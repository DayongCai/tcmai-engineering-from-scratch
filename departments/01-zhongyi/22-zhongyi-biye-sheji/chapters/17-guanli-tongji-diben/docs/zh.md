# 第 17 章 · 对不上的数不是笔误，是没有人负责计数

> **MOTTO:** 「不明于计数而欲举大事，犹无舟楫而欲经于水险也」——《管子·七法》
>
> **PROBLEM:** 现算口径为 9 院系、187 学科、2,093 章节目标、11,457 学时；同一组数在内容看板、README 计数块、各课 chapters.json 里各写一份。可复算的判据是「差异条数」——四处比对下来若不为 0，就说明至少有一处还写着旧数。
>
> **双根因定位:** 环境逼迫（机构报表以章节与学时为口径，数字不一致会被上级退回）+ 知识积累（本库已有一套现算脚本，可逐项比对）

## 一、命题与数据锚点：三个文件，同一个数

本章的命题是：**同一组数字在三个文件里是否一致，不一致能否自动查出**。这是一个看起来很笨的题目，笨到很多人不愿意做；但它是所有报表类毕设的地基，因为一个数对不上，后面所有分析都会被怀疑。

现算口径摆清：

| 项 | 数 | 来源 |
|---|--:|---|
| 院系 | 9 | 目录结构 |
| 学科 | 187 | 各系学科目录 |
| 章节目标 | 2,093 | 课程计划 |
| 学时 | 11,457 | 课程计划 |
| 比对处 | 3 处以上 | 看板／README／chapters.json |
| 差异条数 | 应为 0 | 比对脚本输出 |

三个数各有来源，各有口径。「院系 9」来自目录层级，「学科 187」来自各系目录计数，「章节目标 2,093」与「学时 11,457」来自课程计划。口径不清时，同一个「学科」可以数成 187，也可以数成 190：多出的三个可能是新建未排课，也可能是重复目录。

这正是本章要解决的问题：**不是数字错，是没人负责计数**。目录是各系自己建的，看板是脚本生成的，README 是手写的；三处各有各的维护者，谁也没义务保证一致。于是每次改完目录，总有一处落后。

比对脚本的作用不是「算得准」，是**把不一致暴露出来**。它能做的有限：读三处、逐项比、列出差异行。它不能替你决定哪一处是对的。决定权在人，脚本只负责让差异无处可藏。

还有一个常被忽略的点：数字有「快照」与「现算」两种。快照是某次统计后写死的，现算是每次运行时重算的。README 里的数字多为快照，脚本输出多为现算。两类混用，就会出现「昨天还是 187，今天变成 189」的困惑。论文里要写清哪个是快照、哪个是现算。

## 二、分阶段交付物与分工

| 节点 | 时点 | 必交物 | 责任人 | 签收人 |
|---|---|---|---|---|
| 开题 | 第 1–4 周 | 四项口径定义、比对范围、差异清单模板 | 学生 | 开题小组 |
| 中期 | 第 8 周 | 比对脚本 v1、首次差异清单、修复记录 | 学生 | 导师 |
| 预答辩 | 第 12 周 | 破立验证记录（改坏→红→修复→绿） | 学生 | 预答辩组 |
| 答辩 | 第 16 周 | 比对脚本、差异清单、验证记录、复跑记录 | 学生 | 答辩委员会 |

开题要先把四项口径定义写死。什么叫一个「学科」？有目录就算，还是排了课才算？什么叫「学时」？计划学时还是实际排课学时？定义不同，数字就不同，比对也就无从谈起。定义要写进脚本注释，不只写在论文里。

分工上，口径定义由导师确认，脚本由学生写，各系目录的维护责任归各系教学秘书。第三项是关键：比对能查出差异，但修复要落到具体的人。若没有责任人，差异清单会一年一年地累积，最后没人看。

中期要交首次差异清单。清单不必长，但每条要写清：哪一处、哪个数、与现算差多少。常见的差异有三类：数字落后（改完目录没更新 README）、口径不同（一个按目录数、一个按排课数）、笔误（手写时多打一位）。三类处置不同，混在一起就分不清谁该改。

预答辩要做**破立验证**：故意改坏一个数，看脚本报不报警；修回去，看是否转绿。这个动作比任何描述都有说服力——它证明脚本真的在比对，而不是永远输出「一致」。验证记录要留命令与输出，不能只写「已验证」。

### 破立验证的具体做法

第一步，选一个数，比如章节目标，把 2,093 改成 2,094。第二步，跑比对脚本，记录报错原文。第三步，改回 2,093，再跑一次，记录全绿。三步都留输出，附在论文附录。

这个做法的价值在于可复现：评审不信「脚本能查出差异」，但会信一段「改坏后报错原文」。原文里通常带着文件路径与行号，一看就知道脚本读的是哪一处，而不是空转。

破立验证还有一个副产品：它会暴露脚本的盲区。比如脚本只比数字不比单位，改一个「学时」为「课时」不会被发现。发现盲区就补，补完再验一次，这也是一份可写进论文的记录。

## 三、判据与评分维度【教学设定】

数据层判据四条：

| 判据 | 合格线 | 检查方式 |
|---|---|---|
| 口径可读 | 四项各有定义 | 读脚本注释 |
| 比对可跑 | 一条命令出差异清单 | 当场执行 |
| 破立可验 | 改坏即报警 | 看验证记录 |
| 差异可归 | 每条差异有类型 | 清单有列 |

评分维度（教学设定）：

| 维度 | 权重 | 不合格 | 合格 | 优秀 |
|---|--:|---|---|---|
| 命题可判 | 15% | 只说「统一口径」 | 有差异条数判据 | 预写差异类型 |
| 数据可核 | 25% | 四项数说不清 | 可现算 | 分清快照与现算 |
| 比对可复跑 | 25% | 手工核对 | 脚本可跑 | 破立记录完整 |
| 评价完整 | 15% | 不报差异 | 差异有类型 | 修复可追 |
| 移交可用 | 20% | 只交清单 | 清单＋脚本 | 附责任人分工 |

「数据可核」占 25%，因为这一章的价值全在数字能不能被独立复算。评审通常会当场问「187 是怎么数出来的」，答「目录数」还不够，要能说清哪些目录算、哪些不算。说不清，就说明这个数是估的。

「比对可复跑」同样占 25%，看的是脚本能不能被别人跑起来。跑不起来常见于两种情形：路径写死在本机、依赖没有说明。两种都属于移交失败，评分时按不合格计，不看差异清单写得多漂亮。

## 四、记录字段与复算口径

差异台账建议七列：

| 列 | 填什么 | 例 |
|---|---|---|
| 项 | 院系／学科／章节／学时 | 学科 |
| 位置 | 文件名 | README 计数块 |
| 文件值 | 该处写的数 | 185 |
| 现算值 | 脚本算出 | 187 |
| 差 | 现算 − 文件 | +2 |
| 类型 | 落后／口径／笔误 | 落后 |
| 状态 | 待修／已修 | 已修 |

「差」这一列要带符号。只写「差 2」，读者不知是多是少；写「+2」，一眼看出文件落后。符号看似小事，实际决定了清单能不能被快速扫读。

复算口径四条：院系 ＝ 一级目录数；学科 ＝ 各系二级目录数之和；章节目标 ＝ 各课 chapters.json 条目数之和；学时 ＝ 各课学时之和。四条都要写进脚本，改动任何一条都算口径变更，须升版本号。

## 五、失效模式与考核项

| 失效 | 表现 | 拦截 |
|---|---|---|
| 口径混用 | 快照与现算并列 | 标注来源类型 |
| 只比总数 | 分项错而总数对 | 逐项比对 |
| 无责任人 | 差异清单常年累积 | 落到岗位 |
| 脚本空转 | 永远输出一致 | 破立验证 |
| 单位不校 | 学时与课时混 | 值＋单位同校 |

第一条要展开。快照与现算混用最典型的场景，是 README 里写「全库 2,093 章」，而脚本算出 2,095。差两个不是错，是时间差；但读者不知道，会以为有人在虚报。处置办法是在 README 数字旁标注「截至某日」，或在生成 README 时直接注入现算值。

第五条也值得说。单位不校是比对脚本最常见的盲区：数字一样、单位不同，脚本报一致，人一看就错。补法很简单，把「值＋单位」作为一个整体比对，单位不同即报差异。

八条考核项：

- [ ] 能报出四项现算数；
- [ ] 能说清每项的口径；
- [ ] 能指出三处比对位置；
- [ ] 能跑出差异清单；
- [ ] 能演示改坏后报警、修复后转绿；
- [ ] 能给出差异类型与责任人；
- [ ] 能分清快照与现算；
- [ ] 能说明脚本的已知盲区。

补一句对比对的预期：差异不可能长期为 0。改目录、加课程、调计划，都会让某一处暂时落后。目标不是「永远为 0」，而是「每次跑完知道差在哪、多久能修」。把这条写进论文，读者不会因为你交稿当天有两个差异就否定整套方法。

还有一个容易被忽略的比对对象：课程自带的 chapters.json。它既是数据源，也是被比对的文本；若把它自己算出的数写回自己，比对永远为绿，等于没比。处置办法是比对时排除写入方，只比读方与写方之间的差。

这件事听起来绕，实际很常见：脚本读 A 写 B，再拿 B 与 A 比，当然一致。真正的比对要跨文件：看板对 README、README 对 chapters.json、chapters.json 对目录。三角互比，才能发现「两处一起错」的情况。

三角互比还有一个好处：它能定位错在哪一环。两处不一致时，第三处往往能当裁判——三者中两者相同，少数的那一处就是错的。这个思路比逐处修补省事得多。

### 比对脚本该放在哪一步

比对不该放在最后，而该放在每次改目录之后。放最后，差异会积累成一大坨，没人愿意修；放每次改动之后，差异只有一两条，顺手就改了。这个位置的选择，决定了这张表是活的还是死的。

具体做法是把它挂进日常流程：改完目录，跑一次；改完 README，跑一次。跑完只看差异条数，为 0 就继续，不为 0 就当场修。成本很低，收益是数字长期可信。

若没有条件挂进流程，退一步也要在三个节点跑：开题前、中期、答辩前。三次至少能保证「交出去的那一刻是对的」，不至于拿一份半年前的数去答辩。

## 代价与边界

1. 统计口径只覆盖本库，不含院校真实办学数据；本库的 187 学科与 2,093 章节目标是教学过程数据，不是评估指标；
2. 目标章节与学时来自课程计划，属排课期估算，随计划调整而变，不构成办学规模结论；
3. 比对脚本只能发现不一致，不能判定哪一处正确；修复须由目录维护方确认；
4. 商业侧按本库实例：中医医院管理科室与县域医共体客群 6,498 家、取带中位 5.5% 对应 70 家、客单 26,000 元，三年收入 2,236,000 元，回本 9.2 个月——客户为机构，采购周期长；
本章可直接验证：`node code/main.js` 打印结构清点与判据清单（数字从 `docs/zh.md` 现算），`node --test code/main.test.js` 跑本章单测；两条命令只读正文与代码，不写任何文件。
