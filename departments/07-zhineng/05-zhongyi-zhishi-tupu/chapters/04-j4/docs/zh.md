# 第 4 章 · 一棵树值不值钱，取决于它能不能被重跑出来

> **MOTTO:** 「虽未能尽愈诸病，庶可以见病知源。」——《伤寒论·序》
>
> **PROBLEM:** 2,489 片章节叶、103 片病证叶、3,370 条边，靠人抄一遍要几个月，抄完第二天就开始过期。教材改一个字、加一小节，树就与源脱钩，而且没人知道从哪一处开始脱的。所以问题不是「怎么建树」，而是「建完之后，凭什么相信它还是对的」。

**双根因定位:** 环境逼迫（教材每年改版，四类源文件各用不同排版，人工誊录必然漂移且无法定位） + 知识积累（把「一致性」从承诺变成一条可执行命令，需要先有单一构建点、schema 与门禁三件套）

## 一、单一构建点：生成物不许手改

整棵树由一个构建入口一次生成，任何人不得手工编辑生成物。这条规矩看着苛刻，收益却有三层：

- **一致性可证。** 索引、技能挂点、章节叶都从同一份源派生，不可能出现「索引里有、树上没有」。多入口系统里最耗时的 bug 就是这种半同步。
- **规模可扩。** 学科从 120 增到 188，只改源与参数，重跑即可；没有「再手工补一遍」这种选项。
- **可自动判定。** CI 能检查生成物是否已提交、是否与源哈希匹配。于是「树是新的」变成一个通过/失败，而不是一句声明。

配合的是一条很朴素的纪律：**源层只读，带指纹。** 入库的 Excel 原样保存并记 sha256，改内容必须换文件、换指纹，不允许就地编辑。这样任何一次数据变动都能追溯到「哪一版源」。

管道方向也必须单向：

```text
源层（xlsx/pdf，只读带指纹）
  → 单元层（standards/<学科>/units.json，事实源）
  → 骨架层（须/根/干/枝）
  → 叶层（知识点 + 出现位置 + 出处）
  → 关系/簇层
  → 视图层（可删可重建）
  → 交付层（站点、目录、智能体工具）
```

视图回写上游一律视为 bug。原因很实在：视图是投影，投影一旦能改原件，「哪个才是真的」就永远说不清。学派视图、朝代视图、院系视图都属这一类——它们可以随时删掉重建，不应承载任何独有信息。

## 二、四类源、四种排版：容错解析是主战场

树的输入跨四类异构文件，各有各的脏法：

| 源 | 形态 | 主要坑 |
|---|---|---|
| 学科目录 | JSON | 字段命名不统一，编号有前导零 |
| 领域规范 | Markdown | 同一份表用了四种排版（见下） |
| 病证单元 | JSON | 复合键（病名 + 空格 + 编码）不能直接去重 |
| 技能目录 | JSON | 声明的学科号可能已废弃 |

最麻烦的是 Markdown 规范里的目录，它至少有四种写法：编号列表（`1.1 xxx`）、Markdown 表格（`| 1.1 | xxx |`）、`<br>` 拼接在单元格里的一串、以及代码围栏内的人工排版。构建器必须逐策略尝试，并且**带章节归属追踪**——抽到一个标题后，得知道它属于哪一章哪一节，否则抽出来的叶没有父，违反「无孤儿」门禁。

经验上，容错解析的判据不是「能抽多少」，而是「抽不到时怎么办」。正确做法是**告警不中断**：某学科一片叶都没抽到，构建继续，日志里留一条「该学科章节叶 0，疑排版未识别」，然后回源修排版。若改成中断，一个人修不好就没人能跑通整条管道；若改成静默跳过，缺口就永远藏在统计里。

同理，过滤要留痕。某张表里有一行是表注（「说明：病名对齐 ICD-11……」），它不是数据行。按编码格式过滤掉它没问题，但必须把过滤结果记进日志（`skipped: ["说明"]`）——**静默丢弃与从未存在，在下一个人眼里长得一模一样。**

## 三、Schema：把约定写成可校验的东西

节点与边的结构由一份 JSON Schema 固定：节点必须有 `id / level / level_index / name / kind`，边的 `type` 限定在枚举内。任何越界在构建阶段就被拦下，而不是等到查询时才发现某条边的类型没人认识。

枚举的价值在于它同时是文档与校验器。一份写着「六经限定七值」的说明文档，读的人可能记错，写的人可能漏改；一个枚举，越界即报错。这也是把标准落地的唯一切实方式——标准若只存在于 PDF 里，它就无法阻止任何人写错。

边型的设计要克制。知识树用六类边覆盖全部语义：

| 边 | 方向 | 用途 |
|---|---|---|
| `nourish` | 须 → 根 | 哲学根基滋养公理 |
| `spine` | 根 → 干 | 公理支撑院系域 |
| `leaf` | 枝 → 叶 | 从属（树边） |
| `ref` | 叶 ↔ 叶 | 跨枝引用，必须带理由 |
| `derives_from` | 叶 → 叶 | 历史源流，必须带年代且不得成环 |
| `dsu` | 叶 ↔ 病证单元 | 章节知识点与病证单元的对应 |

六类之外不加。每加一类，都要回答「它能不能被现有六类中的组合表达」——多数情况下能，而多出来的那一类会让所有下游查询都要多写一个分支。

自检脚本把五类断言固化下来：结构完整性（无孤儿、编码非空）、树导航（path 唯一）、图邻接（边端点存在）、检索（关键词能命中）、接口路由（端点可达）。五类断言跑一遍，等于对整棵树做了一次体检；其中「无孤儿」和「边端点存在」这两条能拦住绝大多数构建事故。

## 四、双向绑定：树给结构，向量给语义

树解决「在哪」，解决不了「像不像」。「失眠」与「不寐」在树上相距很远（分属不同学科的不同枝），语义上却是同一个东西。所以需要第二套表示：向量。

绑定是双向的。树的叶文本（名称 + 别名 + 描述）喂进向量库，成为可检索的文档；语义检索的命中结果再回挂到具体的叶上，于是检索结果天然带着位置与出处。这条回挂是整个设计的枢纽——**没有它，向量检索给出的是一段文本；有了它，给出的是一个坐标。**

平台的检索栈值得单独说，因为它刻意避开了大模型：字符 n-gram 分词 → TF-IDF → SQLite FTS5 全文索引（BM25）→ 多通道结果融合（RRF，k=60）。三通道分别是向量相似度、FTS5 词袋、FTS5 子串，融合而非择一。理由是中医术语的查询同时有「概念相近」与「字面包含」两种需求：查「心脾两虚」既希望命中同义写法，也希望命中字面含这四个字的段落。

零 token 起步不是妥协，是取舍。中医标注稀缺，稠密向量在标注不足时容易把「肝阳上亢」和「肝火上炎」混成一个方向；而字符 n-gram 加 BM25 至少在字面上是可解释的——命中了哪几个 bigram，能逐条列出。等单元层规模上来、评估集建好，再升级到语义向量，这条路径比一开始就上大模型更稳。

## 五、上下文工程：只送该送的，不送全库

检索的下游是 LLM，而上限卡在上下文。全库一次性送入既贵又不准——噪声多，模型容易抓错重点。所以要在检索与生成之间加一层装配：

```text
1. path(叶)       → 给出学科坐标（这是哪门课第几章）
2. neighbors(叶)  → 给出关系证据（证候、病证、编码、主方）
3. 按证据等级排序 → A 级在前，F 级在后并标注
4. 只取 Top-k 叶  → 每叶一段结构化上下文
```

装配规则的每一条都有用途：`path` 让回答能落到「哪一章」，`neighbors` 让回答能带依据，按证据等级排序让高可信内容先进入模型视野，只取 Top-k 控制成本。四步合起来，输出才是「结构化、有出处、可复核」的，而不是一段听起来很像的散文。

这里有一处必须写明的技术债：当前知识树只给出各边型的**条数**，不含逐边端点，因此无法从树文件还原完整邻接。`path()` 可用（部分病证单元有学科枝），`neighbors_full()` 尚未实现。这意味着「给一个叶就能列出它的全部邻居」目前还得靠病证图谱侧的数据，而不是树本身。把这条写进教材，比假装接口完备更有用——下一个人接手时不会以为是自己用错了。

同一棵树还能按角色投影出不同的知识边界：医者加载临床与智能域，药者加载中药与方证边，管理者加载管理与质控叶。用 `subtree(域)` 裁剪，而不是另建三棵树。**一份数据、多种视图**，这与前面的单向管道是同一条原则。

树图一体还让两件日常事变得可算。一是**教材目录体检**：用 `path(叶)` 反查任一知识点所属的域—学科—章节，就能自动发现「这门课的教材目录缺了一章」或「这一章挂到了错的枝上」，而不必人工比对两份目录。二是**掌握度核算**：把病证叶按院系与学科聚合，「已掌握多少病证、还差哪几个学科」就直接是计数，成长路径从描述变成报表。这两件事都不需要新数据，只需要位置准确——又回到本章开头那句：树的全部价值，在于它的位置可信且可重算。

## 六、代价与边界

- **构建器是唯一真相，也是单点故障。** 它错了，全树错，且错得很一致。所以构建器必须有测试，而不是「跑通就行」。
- **容错解析有上限。** 排版超出预设四种时仍会漏抽，表现为「该学科叶数为 0」；这类告警必须人工回源，不能靠调参解决。
- **向量层与树层可能不一致。** 叶文本改了而索引没重建，检索会命中旧内容。重建索引要跟着构建一起跑，不能靠记得。
- **`neighbors_full()` 未实现**，逐边端点目前不可从树取得；本章不声称该能力已可用。
- 本章讨论的是构建与检索工程，不涉及任何临床判断。
