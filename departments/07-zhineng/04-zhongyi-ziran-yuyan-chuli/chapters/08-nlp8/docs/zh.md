# 第 8 章 · 规则不是模型的补丁，是模型的天花板

> **MOTTO:** 张仲景：「观其脉证，知犯何逆，随证治之。」——《伤寒论·辨太阳病脉证并治上》
>
> **PROBLEM:** 底本第 8 章 13 个单元、11,644 汉字，讲的是规则学习：序贯覆盖、剪枝、一阶规则（FOIL）、归纳逻辑程序设计。这一章的方法本身没有问题，问题在于它的位置：教材把规则当成「在没有足够数据时退而求其次的方法」，而在中医文本处理里，规则的位置正相反——条文本身就是一份写好的规则库，模型是在规则覆盖不到的地方做补充。位置搞反，系统就会用统计去覆盖条文，用相似度去替代禁忌。

**双根因定位:** 环境逼迫（中医的核心知识以条文形式存在，条文是「条件—结论」结构，天然可读成规则；而条文数量有限、表述古奥，统计方法难以从中稳定学到条件组合） + 知识积累（规则与统计的仲裁顺序没有领域共识，工程上默认「模型优先、规则兜底」，这个默认在医疗场景里是反的）

## 一、条文就是规则库

「太阳病，头痛发热，汗出恶风，桂枝汤主之。」把这句话读成规则，只需要三步：

```text
IF  病位 = 太阳
AND 症 ∋ {头痛, 发热, 汗出, 恶风}
THEN 方 = 桂枝汤
WITH modality = 主之
AND  source = 伤寒论·辨太阳病脉证并治上
```

这不是把古文翻译成逻辑的修辞练习，而是条文本身的结构：前半句是条件（脉证），后半句是结论（方），中间用「者」连接。中医条文的典型句式就是「……者，……主之」，这个句式在《伤寒论》里密集出现，所以**条文可以直接被解析成规则，不需要先训练一个模型**。

这也解释了为什么规则学习的方法（序贯覆盖）在中医文本上特别贴：序贯覆盖的做法是「找一条能覆盖一批正例且不覆盖反例的条件组合，覆盖掉这些正例，再对剩下的重复」。而条文正是这么写的——一条条文覆盖一类证，下一条条文覆盖剩下的情形。二者的结构同构。

同构不等于等价。条文有它自己的问题：条件是隐含的（「太阳病」三个字里含着脉浮、头项强痛），结论是有条件的（「主之」只在没有兼证时成立），而条文之间的覆盖关系并不严格互斥（合病、并病时两条条文同时适用）。规则学习要处理的三件事——条件生成、覆盖判定、冲突消解——在条文上一样都不少。

## 二、规则学习的两个动作：生长与剪枝

序贯覆盖的核心是两个相反的动作。

**生长**是往规则里加条件，使它更准。初始规则可能只有 `THEN 方=桂枝汤`，覆盖所有含桂枝汤的条文；加一个条件 `症 ∋ 汗出`，覆盖缩小；再加 `症 ∋ 恶风`，再缩小。每加一个条件，覆盖的正例减少、反例也减少，直到反例为零或条件用尽。

**剪枝**是往回删条件，使它更稳。生长容易过拟合：为了让反例归零，规则可能加上「脉缓」这种只在这一条里出现的条件，于是这条规则只覆盖一条条文，泛化能力为零。剪枝用留出集判断：删掉某个条件后，若在留出集上的表现不降，就删掉。

两个动作的判据都是**覆盖与精度的权衡**，而权衡的锚点是一个容易忽略的东西：什么算「反例」。在中医条文上，反例的定义本身有争议——一条「桂枝汤主之」的条文，如果病人同时有「无汗」，它还适用吗？严格说「汗出」是条件之一，无汗就不满足；但临床上有「桂枝汤证而汗不出」的变通。规则学习必须先把这类边界定死，否则反例的集合是浮动的，学出来的规则也不稳定。

一个可操作的做法是把条件分两级：**硬条件**（方证对应的核心见证，缺一不可）与**软条件**（常见但可缺的兼证）。硬条件进规则的前提，软条件进权重。这个分级在条文里往往没有明写，要靠注家与教材补——也就是说，规则学习的第一步不是算法，是给条文做条件分级。

分级做完还要面对一个更细的问题：条件之间的冗余。「发热」与「恶热」在多数条文里同时出现，若两条都进硬条件，规则会过窄——临床上有恶热而不发热的情形。判据是条件之间的蕴含关系：若 A 成立时 B 几乎总成立，就只保留 A，把 B 降为软条件。这类蕴含关系可以由语料统计给出候选（共现率极高且方向单一），但确认仍要人判，因为统计上的蕴含与医理上的蕴含不是一回事——「脉浮」与「发热」共现率高，但两者互不蕴含，都可能是独立的辨证依据。

## 三、仲裁顺序：谁说了算

规则与模型同时给出结论时，谁优先？工程上的默认是「模型优先、规则兜底」，理由是模型泛化好、规则覆盖窄。这个默认在医疗场景里应该反过来。

本课采用的顺序是四层，从硬到软：

1. **值域与硬约束**：编码必须在枚举内、六经必须七值之一、配伍禁忌不得放行。这一层是校验，不是预测，违反即拒绝。
2. **条文规则**：有明确条文支持的条件—结论，优先于任何统计结论。
3. **统计模型**：条文覆盖不到时，用相似度或分类器给候选，输出必须标「无条文支持」。
4. **人**：以上都给不出，或给出冲突，退回人判。

这个顺序的道理在于**错误的可解释性**。第一层错了，是数据错误，可以定位到字段；第二层错了，是条文理解错误，可以定位到条；第三层错了，只能说「模型认为」，无法定位。医疗系统里，无法定位的错误比错误本身更危险——因为它不能被复核，也就不能被纠正。

顺序反过来的后果很具体：模型先给出一个方，规则再「兜底」检查禁忌。这时规则只起到了过滤器的作用，而模型已经决定了候选集。如果模型的候选集里根本没有正确的方，规则再严也救不回来。

## 四、冲突消解：两条规则给出不同方

冲突在中医条文里是常态，不是异常。合病时太阳与阳明同病，两条条文都适用；兼证时两个方的适应证同时出现。消解要有明确规则，不能靠「取分数最高的」。

三条判据，按优先级：

**其一，条文层级**。原文优先于后世注，后世注优先于教材归纳，教材归纳优先于统计关联。这一条解决「谁说」的问题：同一件事，《伤寒论》原文与一本现代教材说法不同时，原文优先。

**其二，专指度**。条件多的规则优先于条件少的。「太阳病，头痛发热，汗出恶风」比「太阳病，发热汗出者」专指，两者都命中时取前者。这与序贯覆盖的「先覆盖特例」是同一个道理。

**其三，合方与加减**。两条规则同时命中且分属不同经时，正确输出往往不是二选一，而是合方或加减方。这一条不能由规则自动生成——合方是临床决策，系统的正确行为是**报告冲突并要求人判**，而不是自己合成一个方。

第三条尤其重要。自动合成方剂在文本上看起来合理（两个方名拼起来就是一个合方名），在临床上是一次没有依据的处方。系统的边界在这里：它可以指出「两条条文同时适用」，不能指出「所以用某合方」。

## 五、规则的维护成本

规则库是会腐烂的资产。三条腐烂路径，每一条都需要制度应对。

**其一，条文版本变化**。不同版本字句不同，同一条规则依据的原文可能在某版本里不存在。所以每条规则必须带 `source`（书名·版本·篇名），版本变了要重新核。

**其二，覆盖漂移**。新语料进来后，某条规则可能开始误命中（比如一份病历的写法让「汗出」出现在否定语境里）。所以规则要有回归测试集：一组固定的、人工确认过的样本，每次改规则都跑一遍。

**其三，规则之间的隐性冲突**。规则少时冲突可枚举，规则上百条后冲突是指数级的。缓解办法是分层——把规则按「病位—病性—方」三层组织，冲突检查只在同层内做，跨层用优先级。这一条与第 1 章「树管层次、图管关系」的分工是同构的。

维护成本常被低估，因为它不在开发期发生。一个规则库上线时可能有 200 条规则、冲突 5 处；一年后规则涨到 800 条，冲突 200 处，而这 200 处里有一半是没人记得为什么加的。规则库的价值不在于条数，在于每条都能说清「依据哪条、谁加的、什么时候失效」。

所以规则要像代码一样管：进版本库、有测试、有负责人、有废弃标记。废弃比新增更重要——一条不再适用的规则若只删不记，后来人会重新加回来；留一个 `deprecated` 标记与理由，才算真正处理过。这套做法听起来笨重，但它换来的是可审计：任意一条输出，都能追到「哪一版规则、依据哪条、谁批的」。在医疗场景里，这个链条比规则本身的覆盖率更值钱。
