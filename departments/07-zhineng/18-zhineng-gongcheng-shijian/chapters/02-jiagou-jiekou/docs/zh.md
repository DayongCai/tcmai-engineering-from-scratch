# 第 2 章 · 接口定不下来，架构就只是画在纸上的分工

> **MOTTO:** 「天有时，地有气，材有美，工有巧，合此四者，然后可以为良。」——《周礼·考工记》
>
> **PROBLEM:** 一个区域中医馆的健康档案对接，涉及 5 个系统、37 个交换字段。计划里联调 3 周，实际做了 9 周。延期不来自技术难点，来自三件事：「检查号」在三个系统里分别指申请单号、报告号与设备流水号；「性别」有系统存 M/F，有系统存 1/2，有系统存「男/女」；时间字段一个带时区一个不带，跨零点后的记录全部错位一天。每一次澄清都要开会、改代码、重跑数据，一轮 3 到 5 天。**接口不是实现完之后再对齐的东西，它是实现之前必须冻结的契约。**
>
> **双根因定位:** 环境逼迫（医院既有系统由不同厂商在不同年代建设，字段语义由各家历史决定，没有任何一方有权单方面统一）+ 知识积累（团队把接口当成「调通即完成」，缺少契约先行、语义显式、失败可预期的工程习惯；于是每次集成都在用调试代替设计）

## 一、架构决策要留痕：一页纸的 ADR

架构讨论的默认结局是「会上说过了」。三个月后新人问「为什么用消息队列不用直接调用」，没人答得上来；半年后想改，也说不清当初否掉了什么。解决办法不是写更长的设计文档，而是每个不可逆的决定留一页纸：

| 字段 | 内容要求 |
|---|---|
| 编号与日期 | ADR-007，2026-03-11 |
| 状态 | 提议 / 已采纳 / 已废弃 / 被 ADR-011 取代 |
| 背景 | 三五句，写清约束：并发量、数据量、既有系统、合规要求 |
| 决策 | 一句话，用「我们将……以便……」句式 |
| 被否方案 | 至少两个，各写一句否掉的理由 |
| 后果 | 接受了什么代价：运维复杂度、厂商绑定、迁移成本 |
| 复核日 | 具体日期，到点强制重看 |

被否方案这一栏是关键。没有它，ADR 退化成会议记录；有了它，半年后的争论可以接着上次的结论往下走，而不是从零开始。一个中等规模项目，整个周期内值得写的 ADR 通常不超过 15 条；超过 30 条说明在拿文档替代决策。

哪些决定值得写：跨系统的数据流向、同步与异步的选择、标识符的生成规则、多租户与数据隔离方式、模型推理放在端侧还是服务端、第三方组件的引入。哪些不值得写：目录结构、命名风格、日志格式——这些进规范，不进 ADR。

## 二、先把契约写死，再写实现

契约的核心不是路径和动词，是**每个字段的语义**。下面这张表是接口文档里真正有用的部分，一个字段一行，七列缺一列就会在联调时被问一次：

| 字段 | 类型 | 必填 | 取值域 | 单位/格式 | 缺失语义 | 示例 |
|---|---|:--:|---|---|---|---|
| patient_id | string(32) | 是 | 本院主索引 | 大写字母+数字 | 不允许缺失 | ZY20260311000127 |
| visit_type | enum | 是 | outpatient/inpatient/emergency | — | 未知填 unknown，不得留空 | outpatient |
| tcm_syndrome | string(64) | 否 | 证型标准词表 | UTF-8 | 空串表示「未辨证」，不表示「无证」 | 肝郁脾虚 |
| measured_at | string | 是 | ISO 8601 | 带时区偏移 | 不允许缺失 | 2026-03-11T09:20:00+08:00 |
| tongue_img_uri | string(512) | 否 | 受控存储路径 | 相对路径 | null 表示未采集，禁止用空串 | /obs/2026/03/xxx.jpg |
| confidence | number | 否 | 0–1 | 三位小数 | null 表示模型未输出，禁止填 0 | 0.873 |

「缺失语义」这一列是分出工程水平的地方。空串、null、0、缺字段，四种情况在很多系统里被混为一谈，结果是「未采集」被统计成「阴性」，「模型未输出」被当成「置信度为零但仍有结论」。**每一个可空字段都必须声明它的空值含义**，且只允许一种表示法。

另外五项必须写进契约：

1. **幂等键**。写接口带 `Idempotency-Key`，同一键重复提交返回首次结果，不重复落库。没有幂等键的重试一定会在网络抖动时造出重复记录。
2. **错误码分段**。4xx 段按来源分：400 参数格式、401 未认证、403 无权限、404 对象不存在、409 状态冲突、422 语义不合法；5xx 段按责任分：500 自身缺陷、502 上游异常、503 限流、504 超时。每一段配一句「调用方该怎么做」。
3. **分页与排序**。游标分页优先于偏移分页，排序字段必须唯一且稳定，否则翻页会漏记录。
4. **超时与重试约定**。服务端承诺 P95 延迟，调用方按承诺值设超时，而不是拍一个 30 秒。
5. **版本标识**。路径带主版本 `/v1/`，字段只增不删不改语义；要改语义就开新版本。

契约的落地形式建议用机器可读的 schema（OpenAPI 或 protobuf），文档从 schema 生成，避免文档与实现两张皮。schema 进仓库，改动走评审，和代码同等待遇。

## 三、集成模式与失败处理

同步、异步、批量三种模式各有明确的适用面，选错会在半年后以「系统卡死」的形式暴露：

| 模式 | 适用 | 不适用 | 典型故障 |
|---|---|---|---|
| 同步调用 | 用户等待中的查询，延迟预算 <1s | 长事务、跨机构、可重试的写 | 上游慢导致线程池耗尽 |
| 异步消息 | 事件通知、最终一致、削峰 | 需要立即读到自己写入的场景 | 消息重复、乱序、丢失 |
| 批量对账 | 大批量同步、日结、补偿 | 实时性要求高的场景 | 全量重跑打断在线业务 |

失败处理参数不要凭感觉给，写成表并纳入配置：

| 参数 | 建议起点 | 依据 |
|---|---|---|
| 连接超时 | 1s | 内网 RTT 通常 <10ms，留两个数量级 |
| 读超时 | 3s | 取上游 P99 的 1.5–2 倍 |
| 重试次数 | 3 次 | 超过 3 次多半不是瞬时故障 |
| 退避 | 1s / 2s / 4s + 抖动 | 避免同步重试形成尖峰 |
| 熔断阈值 | 10 秒内失败率 >50% | 低于此值熔断会误伤 |
| 熔断恢复 | 半开，放 5% 流量试探 | 直接全量恢复易二次雪崩 |

三条硬规则。**只重试幂等操作**，非幂等的写要么加幂等键，要么不重试。**重试必须带抖动**，否则一批调用方会在同一毫秒一起重发。**必须有对账**：异步链路每天跑一次数量与金额的双向核对，差异超过 0.1% 就告警；没有对账的最终一致，实际上是不一致。

## 四、联调：把「碰运气」改成「按清单走」

联调延期几乎全部发生在前 48 小时，因为双方都在发现「约定的事没做」。把准备做成清单，进门先对一遍：

1. 双方契约版本号一致，schema 的哈希值相同；
2. 测试环境地址、账号、证书已互换并验证可用；
3. 每个接口都有一份最小可用样例数据，含空值、边界值与超长值；
4. 时间同步已确认，双方都用带时区的格式；
5. 错误码对照表已交换，每个码都有对应的界面表现；
6. 限流阈值与配额已告知；
7. 日志里能按同一个 request_id 串起两端；
8. 回滚方案已确认：任一方出问题，10 分钟内能退回旧版本；
9. 联系人与升级路径已互留，含非工作时间电话；
10. 联调窗口避开门诊高峰，明确每日可用时段。

第 7 条最值得坚持。两端日志能按同一个 `request_id` 串起来，排障时间可以从小时级降到分钟级；不能串，就只能靠时间戳猜，而时间戳往往差几秒。

接口验收按八项判定，全部通过才签字：字段语义与契约一致；空值与缺失按约定表现；错误码全部覆盖；超时与重试行为符合约定；并发 50 时 P95 在承诺值内；重复提交不产生重复数据；鉴权与越权访问被正确拒绝；日志与审计字段完整。

联调期间每天下班前发一份三行日报：今天通了哪几个接口、卡在哪一条、明天需要谁在场。三行足够，超过三行就没人看。

## 五、演进：兼容是设计出来的，不是运气

接口一旦有第二个调用方，改动成本就不再由你决定。三条规则可以把成本压住。

**只增不改。** 新增字段要给默认值语义，老调用方不传也能工作；删除字段先标记 `deprecated`，保留至少两个发布周期；修改语义等于新建字段，旧字段冻结。**版本走路径，不走参数**：`/v1/`、`/v2/` 并存，v1 的维护期在发布 v2 时书面约定，通常不少于 90 天，到期前 30 天与 7 天各发一次提醒。

**契约测试进流水线。** 每个调用方维护一份「我依赖的字段与行为」测试，服务端每次提交都跑一遍全部调用方的契约测试。这样破坏性改动在合并前就会失败，而不是在对方上线后才发现。契约测试覆盖不到 100% 字段时，至少覆盖所有必填字段、所有枚举值与所有错误码。

**弃用要有账。** 维护一张表：接口、版本、调用方、最后调用时间、约定下线日、迁移负责人。最后调用时间为空但表里还挂着，说明有人偷偷在用，先查日志再谈下线。没这张表，所有「可以下线了」的判断都是猜的。

一个常见误区是把「兼容」理解成「永不改动」。真正的兼容是给调用方留出可预期的迁移窗口：新版本先上、旧版本继续跑、文档与样例同步、迁移有负责人和日期。全部旧调用方迁移完成之前，旧版本不能停——这条写进发布规范，比任何口头承诺都管用。
本章可直接验证：`node code/main.js` 打印结构清点与判据清单（数字从 `docs/zh.md` 现算），`node --test code/main.test.js` 跑本章单测；两条命令只读正文与代码，不写任何文件。

## 代价与边界

- 本章的延迟、重试、熔断参数均为**工程起点值**，须按实际链路 RTT、上游 P99 与业务容忍度重新标定；照搬会在高延迟链路上造成误熔断。
- 契约先行的前提是接口边界已相对稳定。探索期的一次性原型不必写完整契约，但一旦有第二个调用方，契约即为强制项。
- ADR 只能记录决策，不能保证决策正确。复核日到点必须真看，否则它只是一份更长的文档。
- 本章不评价任何具体厂商的接口实现，也不涉及特定的互操作标准条文；实际对接须以现行国家标准、行业规范与双方签署的接口协议为准。
- 兼容策略会带来长期维护成本：每个并存版本都增加测试与排障面。版本数量应设上限，超过即强制迁移。
