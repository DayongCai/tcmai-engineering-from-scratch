# 第 11 章 · 延迟与单价不是运维指标，是临床能不能用的门槛

> **MOTTO:** 「去无用之费。」——《墨子·节用上》
>
> **PROBLEM:** 演算设定：日均 800 次问答，每次输入约 1,800 token、输出约 600 token，每月 22 个工作日。假想单价为每百万 token 输入 4 元、输出 16 元，则月成本约 296 元，单次约 0.017 元。这个数字会让很多人直接结论「太便宜，不用优化」。但同一笔账换成延迟：检索 300 毫秒、推理 4 秒、校验 200 毫秒、渲染 100 毫秒，端到端 4.6 秒；若医师每份病案用三次，就是 14 秒的等待。**成本可以摊薄，时间不能**。而若出于隐私必须本地部署，一台 2.4 万元的工作站按三年折旧加电费约 750 元/月——比 API 贵一倍多，但数据不出院。这笔账的正确答案不在单价里，在**数据分级**里。

**双根因定位:** 环境逼迫（门诊时间以分钟计，医师不会为了一次查询等十秒；而大模型的推理延迟与上下文长度近似线性，检索越多越慢）+ 知识积累（部署形态决定的不只是成本，还有可用性、可审计性与升级路径；把它当纯运维问题，会在合规审查时发现「架构上就做不到」——那时改造成本远高于一开始选对）

## 一、四种部署形态，四笔账

| 形态 | 数据在哪 | 月成本（演算） | 延迟 | 可审计 | 适合 |
|---|---|---|---|---|---|
| 公有 API | 出机构 | 296 元 | 中 | 弱（只有输入输出） | 教学、公开资料问答 |
| 私有云托管 | 机构云内 | 800–1,500 元 | 中 | 中（可留日志） | 院内知识库问答 |
| 本地 GPU 服务器 | 机房内 | 750 元起（折旧＋电） | 低（无网络跳） | 强（全链路可控） | 含患者数据的场景 |
| 端侧／工作站 | 诊室机内 | 摊销后更低 | 最低 | 强 | 单机工具、离线环境 |

四行的差别不在「贵不贵」，在**数据能不能出机构**。这一条是硬约束，不能用成本去换。演算设定一条界线：含可识别患者信息的文本，一律不出机构；脱敏后的公开知识问答，可以走 API。两条路并行并不矛盾，多数机构最终是混合的。

还有一个常被漏掉的成本：**运维人力**。本地部署需要有人管驱动、显存、模型版本、故障恢复。这部分不进账单，但真实存在——一个小团队维护一套本地推理服务，每年至少吃掉几十个工作日。选本地之前要先回答「谁来管」。

因此多数机构的实际答案是混合：三级以上数据走本地，一二级走 API，两套共用同一套提示词与校验规则。这样做的前提是**接口抽象**——上层业务代码不认识具体的模型供应商，只认识「生成」与「检索」两个能力。没有这层抽象，混合架构会在第一次切换时崩掉。

## 二、成本算例：钱花在哪一行

把上一段的账拆开：

| 项 | 计算 | 月值 |
|---|---|---|
| 输入 token | $1{,}800\times800\times22=31{,}680{,}000$ | 31.68 M |
| 输出 token | $600\times800\times22=10{,}560{,}000$ | 10.56 M |
| 输入费用 | $31.68\times4$ | 126.7 元 |
| 输出费用 | $10.56\times16$ | 169.0 元 |
| 合计 | — | **295.7 元** |

关键结论：**输出比输入贵 4 倍，而输出只占 token 量的四分之一，费用却占了近六成**。这直接改变了优化方向——压缩提示（输入）省不了多少钱，控制输出长度才省钱。

控制输出长度的正当方式是结构化输出，而不是「请简短回答」。前者把散文换成字段，长度自然下来；后者会让模型漏掉关键信息。演算设定：把一段 600 字的解释换成 8 个字段共 150 token，单次输出费用从 0.0096 元降到 0.0024 元，且可校验。

缓存也值得提一句。同一批常见问题（「什么是表证」）每天被问几十次，命中缓存就不必再推理。命中率不需要很高就有明显收益：演算设定 30% 命中率，月成本降到 207 元。但缓存必须按**知识库版本**失效——知识更新后，旧答案不能继续服役。

## 三、延迟预算：从点击到出字

延迟是唯一不能靠规模摊薄的指标。一次问答的四段：

| 段 | 典型耗时（演算） | 优化手段 | 能否省掉 |
|---|---|---|---|
| 检索 | 300 ms | 索引裁剪、并行两路 | 不能（省掉就无依据） |
| 首字延迟 | 600 ms | 前缀缓存、短提示 | 部分 |
| 生成（600 token） | 3.4 s | 减少输出、流式返回 | 可减 |
| 校验 | 200 ms | 只校验引用编号 | 不能 |

合计约 4.5 秒。这个数字对「查一条条文」太慢，对「整理一份病案」可以接受。所以延迟要**按任务分档**，而不是给一个统一目标：

- 速查类（条文、术语）：目标 2 秒内，手段是短输出＋流式。
- 整理类（病案结构化）：目标 10 秒内，可以多步检索。
- 分析类（多方案对比）：目标 30 秒内，允许异步＋进度提示。

**流式返回是这里最有效的单项改进**：总时长没变，但首字在 0.9 秒出现，使用者感知的等待从 4.5 秒降到 1 秒。这不是错觉，是人机交互的基本事实——有反馈的等待比无反馈的短等待更可忍。

反过来，最差的组合是「长检索＋非流式＋长输出」：用户盯着转圈十几秒，然后一次性看到一大段。技术上没有错，体验上不可用。

## 四、并发与显存：本地部署的真实天花板

本地部署常被低估的地方不是权重，是**缓存**。自回归生成的每一步都要复用前面所有 token 的键值对（KV 缓存），这部分随上下文长度线性增长。

演算设定一个 7B 级模型，32 层、32 个注意力头、每头维度 128，半精度：

$$\text{KV 每 token}=2\times32\times32\times128\times2\ \text{字节}=524{,}288\ \text{字节}\approx0.5\ \text{MiB}$$

一个 4,000 token 的会话占约 1.95 GiB。量化后权重约 4.5 GB，那么一张 24 GB 的卡装下权重后还剩约 19 GB，理论上能并行约 8–9 个长会话。**这就是「一张卡能同时服务几个人」的真实答案**，而不是「模型多大」。

三个直接推论：

- **长上下文很贵**。把上下文从 4k 提到 32k，单会话的 KV 涨 8 倍，并发数掉到个位数。所以「把整本病案集塞进去」在本地部署里几乎总是错的。
- **并发与延迟反向**。多路并行会摊薄每路的算力，单路变慢。门诊高峰若要保证首字 1 秒内，就得限制并发或加卡。
- **短会话便宜得多**。把每次问答控制在 1,500 token 内，同样一张卡能服务的人数是 4k 上下文的 2.6 倍。**上下文预算是最有效的容量杠杆**，比换卡便宜。

## 五、隐私与本地化：先分级，再选架构

数据分级不是合规部门的文书工作，它直接决定架构。

| 级别 | 内容 | 允许去向 |
|---|---|---|
| 一级 | 公开教材、典籍、规范条文 | 任意，含公有 API |
| 二级 | 脱敏病案（无姓名、无精确日期、无机构） | 私有云；出机构须评估 |
| 三级 | 可识别个人健康的原始病案 | 仅院内，不出机构 |
| 四级 | 特殊类别（如精神、传染、遗传相关） | 院内且需额外授权与留痕 |

第二级的「脱敏」要具体：姓名、身份证、电话、住址、精确日期、就诊号、影像号都要处理，且**自由文本里的间接标识**（「某村唯一的赤脚医生」这类描述）也要处理。只删字段不检查文本，是常见的假脱敏。

第三、四级的数据一旦进入上下文，就同时进入了日志、缓存、向量库。所以「本地部署」的范围必须覆盖**整条链路**：检索索引、缓存、日志、备份。只把推理放本地、把向量库放云端，等于没做本地化——检索时送出去的正是病案原文。

还有一条常被忽略：**提示词本身就是数据**。若把整份病案贴进提示，那么提示日志就是一份病历副本。日志的保存期限、访问权限、加密要求，与病历同等级。

## 六、更新：知识与模型两条不同的节奏

| 对象 | 变化频率 | 更新方式 | 验证成本 |
|---|---|---|---|
| 提示词／规则 | 周 | 改配置，即时生效 | 低（跑回归集） |
| 知识库 | 月 | 重建索引 | 中（抽样核对＋回归） |
| 模型权重 | 季／年 | 换版本，灰度 | 高（全量评测＋人工） |
| 术语表 | 不定期 | 版本化，带迁移 | 中（影响面分析） |

四行的关键差别是**回退成本**。提示词改错了，改回来一分钟；模型换错了，回退要重新部署、重新评测。所以更新策略应当按回退成本分级：回退便宜的可以快，回退贵的必须灰度。

灰度怎么做：先给 5% 的流量用新版本，对比同一批固定问题的输出差异，人工看 50 条。差异里若出现「新版本更短但漏要点」或「新版本引用了旧知识库的条目」，就停下来。这个流程听起来笨，但它比「全量上线后发现不对」便宜得多。

最后一条纪律：**知识更新必须触发缓存失效与评测重跑**。知识库换了版本，旧答案的缓存必须清；评测集里涉及改动条目的题必须重跑，否则分数是上一次的。

还有一条实践建议：给每次发布打一个「组合版本号」——提示词 V12 ＋ 知识库 V7 ＋ 模型 M3。出问题时先看这个三元组，比逐项排查快得多。**系统的问题定位能力，取决于它能不能被指认为某一个确定的组合**。
本章可直接验证：`node code/main.js` 打印结构清点与判据清单（数字从 `docs/zh.md` 现算），`node --test code/main.test.js` 跑本章单测；两条命令只读正文与代码，不写任何文件。
