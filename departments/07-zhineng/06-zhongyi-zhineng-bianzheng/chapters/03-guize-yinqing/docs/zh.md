# 第 3 章 · 规则引擎的天花板，是它写不出的那条例外

> **MOTTO:** 「气相得则和，不相得则病。」——《素问·至真要大论》
>
> **PROBLEM:** 规则库写到第三百条时开始互相打架：一条说「脉沉细 + 畏寒 = 阳虚」，另一条说「脉沉细 + 口干 = 阴虚」。病人两样都有，引擎按文件行序先命中谁就算谁——把两条规则换个位置，证型就从阳虚变成阴虚，而两个版本都「通过测试」。可解释性在这里变成了可摆布性：每条规则都能读，合起来却不确定。

**双根因定位:** 环境逼迫（规则要给医生看、给质控审、给后来的人改）+ 知识积累（「必具某症」与「但见一证便是」两类判据在同一库里共存，它们的逻辑强度不同，却被写成了同一种 IF-THEN）

## 一、产生式系统的三件套，与它的顺序依赖

一个规则引擎只有三样东西：规则库（IF 条件 THEN 结论）、工作记忆（当前已知的事实）、冲突消解策略（多条规则同时可用时选哪条）。前两样决定它能表达什么，第三样决定它在边界上的行为——而边界恰恰是中医辨证最常见的地方。

冲突消解有几种常见策略：按优先级、按特异性（条件更细的优先）、按最近使用、按文件顺序。前三种至少还有可陈述的理由，第四种最常见也最危险，因为它把「谁先写」变成了「谁更对」。规则库一旦超过几十条，文件顺序就成了一份隐式的权重表，而这份权重表没有人审过。

判断一个引擎是否可靠的第一个测试是**交换律测试**：把规则文件的行随机重排若干次，对同一批病例重新推理，看结论是否变化。变化率不为零，说明系统的输出依赖书写顺序，不依赖证据。这个测试不需要标注数据，只需要引擎本身，应该在每次规则库变更后跑。

| 冲突消解 | 依据 | 可审计 | 在中医规则库里的问题 |
|---|---|---|---|
| 优先级 | 人工赋值 | 是 | 优先级谁定、依据什么 |
| 特异性 | 条件数 | 是 | 条件多不等于更可信 |
| 最近使用 | 会话历史 | 否 | 同一病人两次调用结果不同 |
| 文件顺序 | 书写位置 | 否 | 隐式权重，无人审 |

## 二、中医规则的四种形态

中医的判据不是一种逻辑。把它全写成同一种 IF-THEN，等于把差别抹掉。

**必具式**是合取，最典型的是六经提纲。「太阳之为病，脉浮，头项强痛而恶寒」，三症并列，构成必要条件组。**但见式**是单条充分，出自方证相应的条文：「伤寒中风，有柴胡证，但见一证便是，不必悉具。」（《伤寒论·辨太阳病脉证并治中》）这句话在逻辑上是很强的断言——某一条特异表现单独就足以支持判断。**计分式**是加权和，处理兼夹与轻重。**排除式**是否定，处理禁忌与危候。

| 形态 | 逻辑强度 | 例子 | 失效方式 |
|---|---|---|---|
| 必具 | 全部条件必要 | 六经提纲 | 一条未采集即整条不触发 |
| 但见 | 单条充分 | 柴胡证 | 特异症被常见病污染 |
| 计分 | 累计超过阈值 | 兼夹证权衡 | 次症堆出主证 |
| 排除 | 出现即否决 | 危候、禁忌 | 排除项没采集，规则空转 |

四种形态混在一个引擎里，必须让引擎知道它们的差别。最省事的做法是给规则加一个 `mode` 字段：`all_of`、`any_of`、`score`、`veto`。`veto` 的优先级应高于一切正向规则，且不参与冲突消解——否决就是否决，不该和别的规则比强弱。

```text
规则 R-017
mode   all_of
when   脉浮 ∧ 头项强痛 ∧ 恶寒
then   太阳病（提纲）
source 《伤寒论·辨太阳病脉证并治上》

规则 R-042
mode   veto
when   舌红绛无苔 ∧ 脉细数
then   否决「阳虚」类结论
```

## 三、冲突从哪来：三个真实来源

规则打架不是写错了，是三种结构性差异在同一个库里碰头。

**症状多义。** 同一个症状可以指向不同病性。「脉沉细」在阳虚是脉道失于鼓动，在阴虚是脉道失于充盈，在气血两虚是双重不足。规则若只写「脉沉细 → 某证」，就是把一个多义信号当成了单义信号。

**证候重叠。** 脾虚湿困与脾阳虚都可以有纳差、便溏、舌淡、脉弱，区别在畏寒程度与湿象轻重。两个证型的规则前件大面积重叠，是正常的，因为证型本身就相邻。问题在于引擎会把重叠读成冲突。

**术语不统一。** 三批人写的规则，一批用「纳呆」，一批用「食欲不振」，一批用「不欲食」。前件看起来不同，指的是一件事；或者看起来相同，指的不是一件事（「不欲食」可以是无食欲，也可以是厌食）。这类冲突在文本层面，不在逻辑层面，靠逻辑检测发现不了。

| 冲突类型 | 检测方法 | 处置 |
|---|---|---|
| 前件相交、后件互斥 | 两两比对前件集合与后件 | 加鉴别条件或降为计分 |
| 前件相同、后件不同 | 完全重复检测 | 合并，或按证据分级拆开 |
| 术语异形同义 | 词典归一后再比对 | 先统一词表 |
| 层级包含 | 证型上下位关系 | 上位规则让位下位 |

静态检测只能查出前两类。第三类要靠词表，第四类要靠本体——这也解释了为什么规则库和质量治理不能分开做。

## 四、覆盖与空洞：最危险的是沉默

规则库有两个指标，比准确率更该先看。

**覆盖**：每条规则的前件，在目标人群的病种分布下能命中多少病例。一条写了三年从未触发的规则，无论写得多漂亮，都是装饰。覆盖率为零的规则要么前件过严，要么对应的证型在这个科室根本不出现——两种情况都该处理，而不是留着占位。

**空洞**：所有规则都不命中时，引擎做什么。这是规则系统最容易出事的地方，因为空洞的默认行为通常不被写进文档。常见默认有三种：返回空（系统宕机式失败，医生认为系统坏了）、返回第一条规则（把书写顺序当答案）、返回最常见的证型（把基础率当判断）。三种都不对。正确做法是显式返回「未覆盖」，并记录未覆盖病例的特征，作为下一版规则的输入。

| 状态 | 含义 | 应输出 | 不应输出 |
|---|---|---|---|
| 单条命中 | 证据支持一个证 | 该证 + 依据 | 概率装饰 |
| 多条命中 | 证据支持多个证 | 候选集 + 主次 | 按顺序取第一 |
| 零条命中 | 证据不足或超纲 | 未覆盖 + 缺失项 | 最常见证型 |
| 被否决 | 出现否决项 | 不成立 + 否决依据 | 降级为次优 |

零条命中率高，说明规则库与该科室的病种结构不匹配，不是模型不够强。先看未覆盖病例长什么样，再决定是补规则还是承认这批病例超出适用范围。

规则库还需要回归测试。每次新增或修改一条规则，都要在固定的病例集上重跑，比对结论变化，并逐条解释变化是否预期。没有回归测试的规则库，改到第两百条时已经没人知道当前版本与三个月前差在哪里。病例集要包含三类：典型病例、边界病例、以及已知的未覆盖病例。第三类最关键，它标记的是系统的能力边界，而不是缺陷清单。

## 五、什么时候该离开规则引擎

规则不是落后技术，它有统计模型给不了的东西：判据可逐条引用、结论可逐条反驳、修改可追溯到某条条文。这些在医疗场景里是硬需求，不是情怀。

规则真正吃亏的地方有三处。**连续变量**：体温、脉率、病程天数，切成「高/低」就丢了斜率信息。**交互效应**：两个症状单独都不指向某证，同时出现才指向——规则要穷举组合，数量爆炸。**罕见组合**：规则由人写，人只会写见过的组合，没见过的永远覆盖不到。

所以现实中的架构多是混合的：规则层管否决、主症与可追溯的骨架，统计层管排序、兼夹与未覆盖病例的兜底。混合的关键是接口清楚——统计层的输出不能覆盖规则层的否决，规则层的结论必须带上条文出处。

混合还有一个工程前提：**事实的表示必须统一**。规则层读的是「症状 = 值」，统计层读的是向量；两层若各自维护一份输入，迟早对不上——同一份病历，规则层看到「无汗」，模型层看到缺失，结论自然打架。可行的做法是先归一化成一份事实表，规则与模型都从这份表取数，任何一侧的字段变更都走同一份 schema 审核。
本章可直接验证：`node code/main.js` 打印结构清点与判据清单（数字从 `docs/zh.md` 现算），`node --test code/main.test.js` 跑本章单测；两条命令只读正文与代码，不写任何文件。

|---|---|---|---|
| 危候否决 | 强 | 弱 | 规则，硬约束 |
| 主症合取 | 强 | 中 | 规则 |
| 兼夹排序 | 弱 | 强 | 统计 |
| 未覆盖识别 | 弱 | 中 | 统计 + 人工复核 |
| 结论追溯 | 强 | 弱 | 规则出处字段 |

## 六、代价与边界

- **维护成本随规则数超线性增长。** 规则之间的潜在冲突对随条数平方增长，每加一条都要与既有条目比对。一个几百条的库，维护它的人力成本会超过开发它的成本。
- **可解释不等于正确。** 每条规则都能读到出处，但出处引用错了、条文理解偏了、或者条文本身有流派争议，引擎照样会自信地输出。规则库必须有专家复核环节，代码测试查不出义理错误。
- **规则会固化某一版教材的口径。** 规则写死之后，教材修订、共识更新都不会自动反映。需要版本字段与定期回看机制，否则库会慢慢变成历史标本。
- **规则不处理「不知道」。** 它能表达「是」与「否」，很难表达「证据冲突、暂不能判」。后一种状态要在引擎层面显式设计，不能指望规则自己长出来。
