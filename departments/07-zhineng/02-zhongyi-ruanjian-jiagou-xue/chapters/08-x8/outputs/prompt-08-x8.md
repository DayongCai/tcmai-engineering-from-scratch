# 上线不是部署的终点，回滚能力才是 · 提示词

## 用途

给「上线不是部署的终点，回滚能力才是」这一章备课或自学时用的提示词。它不生成结论，只把本章的判据、规模和边界摆出来，
让使用者自己走一遍「可部署性必须在架构里留位置 → 三种迁移策略，三种失败代价 → 割接检查单 → 回滚不是把脚本反过来执行」这条链。

## 提示词

```
我在学《中医软件架构学》第 8 章「上线不是部署的终点，回滚能力才是」，本章 8 节 / 3,101 汉字，习题 6 道。
正文见本章 `docs/zh.md`，关键数字由 `node code/main.js` 从正文现算。

请按以下顺序带我走：
1. 先用一句话说清本章要回答的问题，以及它为什么不能直接套用上一章；
2. 按正文小节顺序，逐节给出该节的判据，并指出这一节最容易被误判的那一处；
3. 本章的判据包括（请逐条解释它在什么条件下成立、什么条件下失效）：
   - 无状态或状态外置
   - 配置与制品分离
   - 迁移脚本幂等可重入
   - 能不能承受一次全量失败
   - 业务验证口径
   - 把不可逆操作单独隔离，并推迟到最后
4. 本章自陈的边界（不得越过）：
   - 本章讨论的是**部署与迁移的结构性做法**，不涉及具体的容器、编排、发布工具；技术选型以机构运维能力为准，能力不足时，简单方案优于先进方案。
   - 灰度与并行都要付成本：灰度需要路由层与双份监控，并行需要双份录入与逐日比对。这部分成本必须在立项时计入，否则上线阶段会被压缩成"一次性切换"。
   - 回滚能力有极限：已经对外发送的数据、已经产生的费用、已经完成的诊疗，技术上无法回滚。这类情形只能靠"变更前谨慎、变更后补偿"来处理。

要求：不编造正文没有的数字；引文写到《书名·篇名》级；不确定的地方直接说「正文未展开」。
```

## 边界

本章为软件部署与迁移教学讨论，不构成诊疗、用药或系统运维决策建议；具体操作以现行规范与所在机构制度为准。
