# 上线不是部署的终点，回滚能力才是

## 什么时候用

需要把本章的判断讲清、或检验自己是否讲清时。

## 怎么用

1. 先读 `docs/zh.md` 的 MOTTO 与 PROBLEM 段，确认这一章要回答的问题是什么；
2. 跑 `node code/main.js`，看本章的结构清点与判据词频（数字全部从 `docs/zh.md` 现算）；
3. 按正文小节顺序，逐节说出判据（本章 6 条核心判断见下）；
4. 用 `quiz.json` 的 6 道题自检，答不上就回到对应小节。

## 核心判据

- 无状态或状态外置
- 配置与制品分离
- 迁移脚本幂等可重入
- 能不能承受一次全量失败
- 业务验证口径
- 把不可逆操作单独隔离，并推迟到最后

## 边界

- 本章讨论的是**部署与迁移的结构性做法**，不涉及具体的容器、编排、发布工具；技术选型以机构运维能力为准，能力不足时，简单方案优于先进方案。
- 灰度与并行都要付成本：灰度需要路由层与双份监控，并行需要双份录入与逐日比对。这部分成本必须在立项时计入，否则上线阶段会被压缩成"一次性切换"。
- 回滚能力有极限：已经对外发送的数据、已经产生的费用、已经完成的诊疗，技术上无法回滚。这类情形只能靠"变更前谨慎、变更后补偿"来处理。
- 本章为软件部署与迁移教学讨论，不构成诊疗、用药或系统运维决策建议。
