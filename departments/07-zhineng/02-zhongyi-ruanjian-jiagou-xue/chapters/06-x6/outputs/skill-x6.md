# 没写下来的决策，等于没做过决策

## 什么时候用

需要把本章的判断讲清、或检验自己是否讲清时。

## 怎么用

1. 先读 `docs/zh.md` 的 MOTTO 与 PROBLEM 段，确认这一章要回答的问题是什么；
2. 跑 `node code/main.js`，看本章的结构清点与判据词频（数字全部从 `docs/zh.md` 现算）；
3. 按正文小节顺序，逐节说出判据（本章 6 条核心判断见下）；
4. 用 `quiz.json` 的 6 道题自检，答不上就回到对应小节。

## 核心判据

- 背景、选项、决定、后果、失效条件
- 它记录了甲和乙为什么没被选
- 不可逆或逆转很贵
- 被反复推翻的决策
- 什么情况下应该重新讨论这件事
- 约束是否完整？

## 边界

- 本章的 ADR 格式是**通用结构**，不强制某一套文档工具；落地方式应适配机构的文档习惯与评审流程。
- 写 ADR 有成本：一份一页半，一年十份，大约是一个人两三天的工作量。这个成本远低于一次返工，但必须有人承担，且要计入项目计划，否则永远排在最后。
- ADR 记录的是当时的判断，不是真理。它允许被推翻，但推翻要留痕——这是它区别于"规定"的地方。
- 本章为软件架构与项目管理教学讨论，不构成诊疗、用药或信息化项目决策建议。
