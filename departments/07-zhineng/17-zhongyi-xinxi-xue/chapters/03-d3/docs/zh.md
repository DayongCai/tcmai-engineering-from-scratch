# 第 3 章 · 标准化：标准不是一份文档，是代码里的枚举与校验

> **MOTTO:** 「标准不是文档，而是代码里的枚举与校验。」——教材·第 3 章 3.5
>
> **PROBLEM:** 一份标准发布之后最常见的结局，是装进文件柜，业务系统照旧自由录入。检验标准的地方不在发布会，在一条 INSERT 语句上——值域没约束住，标准就等于零。教材给了个具体现场：同一份病历，A 院写「消渴」，B 院写「糖尿病」，医保系统里是第三个代码。三份数据放到一起，谁也对不上号，而每一份在自己院里都「没问题」。

**双根因定位:** 环境逼迫（上报口径、结算口径、科研口径三套并存，任何一方都不肯先改）+ 知识积累（本章 24 个单元 1,390 汉字，标准化只占开头 6 个单元，表示、数据库、HIS 占了其余——教材把标准当引子，其实它是后面每一节的隐含前提）

## 一、「对不上号」分三层，修法各不相同

标准化解决的从来不是一件事，而是三件，混在一起谈就会用错药：

| 层 | 失败现象 | 该由谁修 |
|---|---|---|
| 术语不统一 | 同一个概念，两个科室两种叫法 | 词表与术语标准（见第 1 章） |
| 编码不统一 | 同一个概念，三套代码互不相认 | 分类与编码标准 + 映射表 |
| 接口不统一 | 代码能对上，但字段名、长度、必填项各写各的 | 数据元与交换格式标准（HL7/FHIR 一类） |

这三层是有顺序的：术语不定，编码无从定；编码不定，接口只能传字符串。工程上最常见的错误是**从接口层开始修**——先定消息格式，再回头发现两边对「证候」的理解根本不是一回事，于是接口里塞进一个自由文本字段，把所有结构化努力又推回原点。

教材 3.1 把标准化的三件事说得更简洁：术语统一、编码统一、接口统一，对应「同一概念同一名称、同一概念同一代码、同一代码可交换」。这三句是可验收的，前两句验收方式是查表，第三句验收方式是拿两份真实报文对拆。

## 二、编码体系是分层的，不能指望一套码管到底

中医药的编码对象至少有六层，每层要解决的问题不同，难点也不同：

| 层 | 编码对象 | 作用 | 中医特有的难点 |
|---|---|---|---|
| 病名 | 疾病分类 | 统计上报、病种管理 | 病证双轨：中医病名与西医病名不是一一对应 |
| 证候 | 证型、证素 | 辨证结论可统计、可比较 | 复合证多（气阴两虚＝气虚＋阴虚），组合会爆炸 |
| 方剂 | 方名与组成 | 处方审核、配伍规律研究 | 同名异方、异名同方；加减后仍叫原名 |
| 药材／饮片 | 品种、炮制、产地 | 药事管理、质量追溯 | 一药多名、同名异物；炮制改变性效 |
| 穴位 | 经穴、经外奇穴 | 针灸记录、设备对接 | 代号与定位描述并存，国际代号与国内习惯并存 |
| 治法 | 治则治法 | 疗效评价、路径管理 | 与证候强绑定，粒度极不统一 |

第三、四两行值得各停一句。**方剂的加减不改名**，是一条几乎无法从编码层面解决的规则：「桂枝汤」加一味芍药仍常被记作桂枝汤，可它的组成已经变了。所以方剂编码必须区分「方名码」与「组成码」，前者管检索，后者管计算；只编方名码的库，做不了剂量与配伍研究。**药材的同名异物**则直接关系安全：木通一药，历史上关木通与川木通混称，前者含马兜铃酸、后者不含，靠名称无法区分，必须靠品种码与基原字段。这类问题不是学术洁癖，编码错一位，临床上就是另一味药。

国际与国内是双层而非单选。WHO 的 ICD-11 首次为传统医学单设章节（TM1，传统医学病证模块一），使中医病证第一次进入国际分类体系；国内则以《中医病证分类与代码》《中医临床诊疗术语》系列等标准为口径。教材的做法是双通道落地：一条记录同时留国际码与国内码，中间靠映射表连接。**标准编号与版本一律以标委会最新发布为准**，教材本身对不确定项标「待核」，本章沿用这条规矩——宁可留空，不臆造编号。

## 三、数据元：把「一个字段」定义到别人能复现

数据元（data element）是最小可交换信息单元，通常要写全六项：名称、定义、数据类型、表示格式、值域、计量单位。看起来繁琐，但这六项缺任何一项，别人就无法在不问你的情况下填对同一个字段。

| 属性 | 示例（示意） | 缺了会怎样 |
|---|---|---|
| 名称 | 舌质颜色 | 同名字段指向不同含义 |
| 定义 | 舌体（非舌苔）整体呈现的主色调 | 舌质与舌苔混填 |
| 数据类型 | 枚举 | 有人填「淡红偏暗」，无法统计 |
| 表示格式 | 单值 | 有人填多个值，分母失真 |
| 值域 | 淡白／淡红／红／绛／紫暗 | 各院自造词，无法合并 |
| 计量单位 | 不适用 | — |

中医数据元有个鲜明特点：**值域多为枚举而非数值**。舌象、脉象、面色、苔质几乎都是枚举型，这带来两个后果。其一，枚举必须封闭，否则「淡红」「淡红偏白」会同时存在，而系统不会报错；其二，枚举的粒度必须在设计期定死，事后加值等于让历史数据带上一段不可比的区间。

还有一条原则比六属性更常被违反：**单一职责**。一个数据元只表达一件事。「舌淡胖有齿痕」写进一个字段，看似省事，实际上把颜色、形态、边缘三个独立观察压成了一个字符串，从此无法分别统计，也无法在其中一个维度上做质量控制。

## 四、表示的三个层次：从字符串到可校验的结构

同一句「恶寒重、发热轻、无汗」可以有三种表示：字符串（原文）、结构化（症状列表与枚举）、向量（数值）。信息学的任务是在三层之间自由转换，而转换的枢纽是模式（schema）。

教材 3.9 说得很准：JSON Schema 既是文档，也是校验器。它对人是一份说明，对机器是一道闸门。示意如下：

```json
{
  "type": "object",
  "required": ["id", "disease", "syndrome", "manifestations"],
  "properties": {
    "id": { "type": "string", "pattern": "^DSU-[0-9]{5}$" },
    "disease": { "$ref": "#/defs/concept" },
    "syndrome": { "$ref": "#/defs/concept" },
    "sixChannel": { "enum": ["太阳","阳明","少阳","太阴","少阴","厥阴","未定"] },
    "manifestations": { "type": "array", "minItems": 1 },
    "evidence": { "enum": ["A","B","C","D","E","F"] }
  }
}
```

两个细节值得注意。第一，`sixChannel` 的枚举里有一个 `未定`。这不是多余——「未定」是一个**判断结论**，而空值只是**没填**；两者混用，统计时会把「专家看了但没归经」的病例算成「数据缺失」，直接把六经分布算错。第二，`evidence` 用 A–F 六级而不用自由文本，因为证据等级一旦可枚举，它才能被排序、被过滤、被审计。

至于向量层，教材 3.10 给了个很务实的起点：中文没有空格，最快的表示不是大模型，而是**字符 n-gram + TF-IDF**。字符 bigram 对未登录词稳健、零依赖、可解释，中医术语边界又特别灵活（「半表半里证」「少阳病」），词典分词很容易切错，n-gram 至少不会因为词典缺词而完全失配。

## 五、数据库与存储模型：多表关联 + 全文索引 + 图

中医药数据的形状决定了存储选型：**多表关联**（病—证—方—药—穴）与**文本为主**。前者要关系库的严谨，后者要倒排索引的速度。一个最小可用的病证库大致是这样：

```sql
CREATE TABLE disease (
  id     TEXT PRIMARY KEY,            -- 概念号，非名称
  name   TEXT NOT NULL,               -- 首选词
  icd11  TEXT,                        -- 可空，未映射即 NULL
  gb     TEXT
);

CREATE TABLE syndrome (
  id     TEXT PRIMARY KEY,
  name   TEXT NOT NULL,
  parent TEXT REFERENCES syndrome(id) -- 证候的上位，支撑扩检
);

CREATE TABLE dsu (                    -- 病证单元：病 × 证
  id          TEXT PRIMARY KEY,
  disease_id  TEXT NOT NULL REFERENCES disease(id),
  syndrome_id TEXT NOT NULL REFERENCES syndrome(id),
  six_channel TEXT CHECK (six_channel IN ('太阳','阳明','少阳','太阴','少阴','厥阴','未定')),
  evidence    TEXT CHECK (evidence IN ('A','B','C','D','E','F')),
  UNIQUE (disease_id, syndrome_id)
);
```

这张 DDL 里有三处是可以直接抄的工程经验：

- **主键用概念号，不用名称。** 名称会改，概念号不改；一旦用名称做主键，改词就要改所有外键。
- **可空字段一律允许 NULL，但「未判定」必须另有枚举值。** `icd11` 为空表示未映射，这是事实；`six_channel` 用 `未定` 表示已判定为不归经，这是结论。两类空缺混同，就会在质量报告里互相掩护。
- **约束写在库里，不写在文档里。** `CHECK` 与 `UNIQUE` 是标准落地的最后一公里；只写在规范文档里的值域，第一天就会被绕过。

文本检索靠倒排索引（如 SQLite 的 FTS5 虚拟表，提供 BM25 排序）。中文这里有个坑：FTS5 的 `unicode61` 分词器不切中文，整段会被当成一个词，检索等于失效。要么入库前预切成字 bigram 并以空格分隔，要么改用 trigram 分词器。这一点不解决，「全文检索」就只是一个能点但没有结果的按钮。

到了「病—证—方—药—穴」的多跳关系，关系库的连表会迅速变丑，属性图更合适（Neo4j 一类，查询语言 Cypher）；而需要形式化推理时，本体（OWL）更合适。教材记的平台做法是双轨：对外用 OWL 承载领域本体，对内用属性图 JSON 承载构建与查询，中间用 schema 桥接。**双轨不是重复建设，是分工**——本体管「说得清」，图库管「查得快」。

## 六、HIS 与中医临床信息化：是接口，不是替代

医院信息系统（HIS）管挂号、收费、医嘱、检验、影像，它的数据模型是按**费用与流程**组织的，不是按**医学语义**组织的。中医临床信息化要补的，正是 HIS 装不下的那一层：四诊信息、辨证结论、方剂与针灸医嘱、疗效评价。

两者的关系常被误说成「上中医系统替换 HIS」，实际上是接口关系。搞错这一点，项目就会陷入「重做一套 HIS」的泥潭——而 HIS 的收费与医保逻辑，重做一遍几乎必然出事故。

在病历层面，中医电子病历（TCM-EMR）的难点是自由文本里的中医语义。主流做法是**叙构结合**：主体保留自然语言叙述（医案的推理过程本身有价值，压成字段就没了），关键要素抽成结构化字段（主诉、舌、脉、证型、方药）。抽取的边界要提前定：抽得太多，医生不愿填；抽得太少，数据无法计算。

临床路径同样要改造。西医路径是节点序列，中医路径必须容纳个体化辨证——同一个病，不同证走不同支路，本质上是一棵决策树而不是一条直线。把中医路径硬做成直线，结果一定是「路径符合率」很高而临床没人用。

「名定而实辨。」——《荀子·正名》。标准化做到最后，就是让「名」与「实」一一对应；对不上的那些，才是要花力气的地方。

## 七、代价与边界

- 本章提到的标准编号与版本，**一律以标委会最新发布为准**。教材对不确定项标「待核」，本章不补猜。
- 数据库示例是**示意结构**，不是任何生产系统的 schema；照抄前须按本机构的值域与权限模型改造。
- 标准化有真实成本：封闭枚举会挡住少数真实病例，接口改造会打断业务。**这些成本必须显式承认**，否则「为标准而标准」会把临床推到对立面。
- 本章不评价任何厂商产品，也不构成药事或临床建议。药材基原与炮制的判定，须依《中国药典》与主管部门规定执行。
