# 第 7 章 · 项目管理与决策支持：CDS 接在哪一步，决定它是提醒还是噪音

> **MOTTO:** 「上工救其萌芽，下工救其已成。」——《素问·八正神明论》
>
> **PROBLEM:** 某院上线临床决策支持（CDS）一年，累计 47 条规则，后台统计显示医师对弹窗的「忽略」率 92%。逐条复盘发现：31 条只在开立时提示风险，不给替代方案；9 条与药品说明书重复但剂量阈值设错，被医师当成误报；只有 4 条在开立前就给出了可点选的替代医嘱。规则本身大多没错，错在**接入点**——提醒出现在医师已经做完决策、只想快点关掉弹窗的那一秒。

**双根因定位:** 环境逼迫（门诊平均接诊时间以分钟计，任何一次打断都要从诊疗思路里抽身，医师对弹窗的默认反应必然是关闭）+ 知识积累（CDS 长期按「规则库 + 弹窗」理解，缺少对工作流节点的分析：同一条知识，放在不同节点，效果可以差一个数量级）。

## 一、项目输在立项，不在上线

信息化项目最常见的失败形态不是「做不出来」，而是「做出来了没人用」。根因往往在立项阶段：目标写成「提升管理水平」，没有基线、没有验收口径，上线后无法判断成败，只能靠感觉。

可验收的立项至少要三样：**基线**（现在这个指标是多少，怎么算的）、**目标**（期望变成多少，用什么口径量）、**边界**（不做什么，哪些科室不纳入）。例如「门诊药房平均取药等候时间由 18 分钟降至 10 分钟以内（口径：挂号缴费完成至发药完成，不含代煎）」——这句话有基线、有目标、有口径，也有排除项，验收时不需要再解释。

立项还要做一件常被跳过的事：**流程现状测量**。不测现状就直接上系统，等于不知道要改的是什么。测量不必复杂，跟三次班、记录每个环节的实际耗时与等待原因，就能发现瓶颈通常在系统之外（比如药房窗口数量、叫号规则），而不是在系统之内。

还要提前想清「谁在系统上线后负责它」。项目组是临时的，运维是长期的；如果上线时没有明确接管部门、没有运维预算、没有变更流程，系统会在半年内退化成「只能看不能改」的状态。这一条在立项书里通常只占一行，但它决定了项目是资产还是包袱。

## 二、需求规格：把形容词换成可执行的句子

需求文档里最危险的词是「友好」「便捷」「智能」「实时」。它们无法验收，也无法开发。

可验收的写法有固定套路：**在什么条件下，系统在多久内，做出什么可观察的动作，失败时怎样**。举例：

| 不可验收 | 可验收 |
|---|---|
| 界面友好 | 常用操作三步内完成，首屏加载 ≤2 秒 |
| 实时提醒 | 检验结果回传后 5 秒内触发，失败重试 3 次并告警 |
| 智能推荐 | 推荐项须显示依据来源与置信度，可一键忽略并记录原因 |
| 数据准确 | 与源系统抽样 200 条比对，一致率 ≥99.5% |

右边这一列同时是测试用例。需求阶段写不出这样的句子，测试阶段就只能靠「感觉差不多」，验收阶段就只能靠关系。

需求变更要有闸门：变更单写清影响范围（涉及哪些接口、哪些报表、是否影响已验收功能）、工作量、上线窗口，由业务与信息双方签字。没有闸门的项目，最后一定延期，而且延期原因无法归因。

## 三、采购与合同：五条必须写进去的条款

系统采购的坑，八成在合同里，而不是在产品里。五条必写：

**数据所有权与导出**。数据归机构，厂商不得用于其他目的；终止合作时须在约定期限内提供完整导出（含结构化数据与附件），格式开放、可验证。

**接口与文档**。接口清单、调用方式、限流、费用、升级兼容承诺。缺这条，二期每接一个系统都要重新谈钱。

**验收标准**。把需求规格里的可验收句子直接写进合同附件，验收按条打勾，不按「整体感觉」。

**源代码托管或退出机制**。定制开发部分应有托管安排（第三方托管、触发条件明确），避免厂商停止服务后系统无法维护。

**运维响应**。分级响应时限（如宕机 30 分钟响应、2 小时恢复），以及未达标的违约责任。只写「7×24 服务」没有意义，要写清什么时候算达标。

评标时最容易失衡的是把价格权重放得过高。信息系统的总拥有成本里，许可费通常只占三成，接口改造、培训、运维人力、以及未来迁移的成本占大头。只看报价，等于只看了三成。

## 四、CDS 的五个接入点

决策支持的效果，取决于它插在医师工作流的哪一步。五个常见接入点，价值与风险完全不同：

| 接入点 | 触发时机 | 合适的形式 | 主要风险 |
|---|---|---|---|
| 开立（CPOE） | 选药/选检查时 | 默认值、可点选替代、剂量校验 | 打断开单，疲劳 |
| 审核（药师） | 医嘱提交后 | 拦截 + 建议 + 强制理由 | 把判断推给药师 |
| 结果回报 | 危急值/异常值产生 | 分级提醒、闭环确认 | 提醒泛滥，真警报被淹 |
| 病历书写 | 书写过程中 | 模板、缺项提示、术语补全 | 模板化，叙述丢失 |
| 出院 | 首页与编码 | 主诊断核对、入组预判 | 诱导高编 |

三条工程原则比规则数量更重要：

**能给默认值就不弹窗**。把常用剂量、常用频次做成默认值，医师不改就通过，改了才校验。这比任何提醒都有效，且不打断。

**弹窗必须带可执行动作**。提示「该患者肾功能不全，注意调整剂量」是无效提醒；提示并给出「按 eGFR 计算建议剂量 → 一键替换」才有效。没有动作的提醒，本质是把决策成本转回给医师，而医师已经在赶时间。

**分级而不是全拦**。致命交互（如禁忌）硬拦截，需理由才能越过；重要但不致命（如剂量偏高）软提示，可忽略但记录；一般提示只进汇总，不打断。全部硬拦的系统，上线一周就会被要求关掉。

一条规则的可维护写法（示意）：

```json
{
  "id": "cds-aki-001",
  "trigger": "medication-order",
  "condition": "patient.eGFR < 30 && drug.class == 'NSAID'",
  "severity": "hard-stop",
  "message": "eGFR < 30 时使用 NSAIDs 肾损伤风险显著升高",
  "actions": [
    { "type": "suggest-alternative", "value": "对乙酰氨基酚" },
    { "type": "require-reason", "options": ["无替代", "专科会诊同意"] }
  ],
  "evidence": { "source": "院内镇痛药使用规范", "version": "2025-03" },
  "owner": "药学部"
}
```

规则要有 `evidence` 与 `owner`。没有出处的规则无法被质疑，也就无法被修正；没有责任人的规则会一直留着，因为没人有权删它。规则库还需要冲突检测：两条规则对同一医嘱给出相反建议时，系统必须能发现，而不是让医师在两秒内自己判断。

## 五、实施、迁移与评价

上线不是终点，是风险最集中的一天。可控的做法是**灰度**：先一个病区、一周，再扩到全院；同时准备**回滚预案**（旧流程至少保留一个月的可用状态、数据双写或可补录）。没有回滚预案的上线，等于把全院业务押在一次发布上。

数据迁移分四步，顺序不能颠倒：盘点（有哪些表、多少行、什么质量）、映射（旧字段到新字段，含值域转换）、试迁（全量迁一次，记录耗时与失败）、对账（关键指标迁移前后一致，差异逐条解释）。跳过对账，迁移就是一次不可验证的数据改写。

评价要同时看过程与结局：

- 过程指标：采纳率、忽略率、平均响应时延、告警量/千次医嘱。
- 结局指标：目标指标（如取药等候时间）、不良事件、平均住院日、用户满意度。
- 反事实：前后对照要有可比性。上线前后病人结构变了、季节性变了，都会让指标变化与系统无关。条件允许时用同期未上线科室作对照，或做中断时间序列分析。

最有价值的评价往往是否定性的：一条规则上线三个月，忽略率 85%，采纳后也没改变结局——那就该下线。规则库的健康度不看条数，看**每条规则是否还有人维护**。

运维阶段最容易失守的是变更管理。医院系统不允许「随时发版」：白天发版出问题，门诊立刻堵。可行的规则是固定变更窗口（如每周二 22:00–24:00）、变更分级（配置改动 / 小版本 / 大版本，对应不同的审批与回滚准备）、以及每次变更后的 30 分钟观察期。变更单要写清影响范围与回滚步骤，回滚脚本必须被实际演练过——写在文档里没跑过的回滚，等于没有回滚。培训也要算进运维：新功能上线不做 15 分钟的科室现场培训，使用率会在两周内掉回原点。

「上工救其萌芽」，决策支持的价值在决策发生之前，而不是在事后追责。判断一条 CDS 是否「上工」，只看一件事：它是否在医师还没做决定时，把一个更好的选项放到了他手边。

## 六、代价与边界

- 本章的规则条数、忽略率均为**演算设定**，用于说明接入点与疲劳的关系，不代表任何机构的上线数据。
- CDS 规则示例为结构示意，不构成用药建议；任何规则上线前须经药学、临床与医务部门审核，并做本地验证。
- 项目管理的「可验收」原则会增加前期工作量，也会拖慢立项速度。这是必要成本：前期省下的两周，通常会在验收时变成两个月。
- CDS 不能替代医师判断，也不能覆盖说明书的法定地位。规则与说明书冲突时，以说明书与院内药事管理规定为准。

**免责声明：** 本章为卫生信息化项目管理与临床决策支持的教学讨论，不构成用药、诊疗或采购建议；具体规则配置与项目实施，须由本机构相应专业部门审核确定。
