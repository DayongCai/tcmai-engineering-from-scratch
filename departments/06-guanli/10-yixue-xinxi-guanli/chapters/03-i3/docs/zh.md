# 第 3 章 · 系统与电子病历：HIS、EMR、LIS 不是三套软件，是三条责任链

> **MOTTO:** 「物有本末，事有终始，知所先后，则近道矣。」——《礼记·大学》
>
> **PROBLEM:** 一次危急值专项检查，抽查某院 24 小时内 3,000 条检验结果，发现 37 条在电子病历里找不到对应的申请单，另有 11 条在 HIS 里计了费却在 LIS 里查不到标本。三方各自的数据都「完整」，合起来却对不上。追下去不是接口断了，而是三个系统对「一次检验」的定义不同：HIS 认为收费成功即成立，LIS 认为标本上机即成立，EMR 认为医师签名归档才成立。

**双根因定位:** 环境逼迫（收费、诊疗、质控三套流程各有自己的时间起点，谁先谁后由业务决定，不由系统决定）+ 知识积累（医院信息化长期按「买系统」组织，缺少按「数据责任」组织的训练：一张表只能有一个权威来源，其余都是副本，副本必须有同步机制与失效标识）。

## 一、职责边界：每张表只有一个权威来源

判断一个系统该管什么，不看厂商的功能清单，只看一条：**这类数据的权威副本（system of record）在谁那里**。其余系统可以有副本，但副本必须能说清同步方式、更新延迟、冲突时以谁为准。

| 数据 | 权威系统 | 常见越界 |
|---|---|---|
| 患者身份、就诊、费用 | HIS | EMR 自建患者表，与 HIS 各一套 |
| 医嘱内容与执行 | CPOE / 医嘱系统 | 护理系统另存一份医嘱并允许修改 |
| 检验申请、标本、结果 | LIS | EMR 直接存结果文本，不回写申请号 |
| 影像与报告 | PACS / RIS | 报告只以 PDF 存在 EMR，不可检索 |
| 病历文书与签名 | EMR | 纸质签名后扫描入库，视为已归档 |
| 手术与麻醉记录 | 手麻系统 | 术后小结在 EMR 重写一遍，与手麻记录不一致 |
| 药品与库存 | 药房系统 | 医嘱系统自建药品字典，规格与药房不符 |

这张表的用法很直接：任何集成需求，先问「谁是权威」，再问「副本怎么校验」。跳过第一步，做出来的就是四条链路各传一份、各改一份，最后靠人工对账。

平台层与基层机构的关系要单独说一句。区域平台常被要求「汇集全部数据」，实际可行的定位是**索引 + 交换**：平台存患者索引、就诊索引与文档位置，原始数据仍在机构；需要时按授权调阅，调阅行为留痕。把原始数据全量复制到平台，短期看查询方便，长期看是两份数据、两套口径、两处泄露面。基层机构系统能力弱，平台还要承担术语转换与格式校验的职责——不是替它存，而是帮它把数据整理成可交换的形状。

越界的根源往往不是技术，而是**采购边界**。HIS 厂商做不了的模块，医院另买一家，两家都不肯让出主数据；于是 EMR 自建一套科室与人员字典，与 HIS 的编码规则不同，排班与权限从此长期错位。合同中不写主数据归属，后面用十年的人力去补。

## 二、集成：从点到点，到消息，到资源

集成方式有三代，每一代解决上一代的某个具体痛点，也带来新的成本。

**点对点**：A 直接调 B 的接口。两家系统时最省事，十家系统时接口数按 n(n−1)/2 增长，二十家就是 190 条链路。改一个字段要通知所有对端，实际结果是没人改，字段含义在各处缓慢漂移。

**集成引擎 + 消息**：所有系统接一个总线，用 HL7 v2 一类的消息传递事件。链路数降到 n，但语义仍埋在消息位置与本地 Z 段里。典型的 ORU 消息：

```
MSH|^~\&|LIS|HOSP|EMR|HOSP|202603110942||ORU^R01|MSG00042|P|2.5
PID|1||P000123||张^三||19700412|M
OBR|1|ORD7781||HBA1C^糖化血红蛋白|||202603110900
OBX|1|NM|HBA1C^糖化血红蛋白||7.8|%|4.0-6.0|H|||F
```

消息能传，但「ORD7781 是哪次就诊的申请」「7.8 是空腹还是随机」这两个问题，v2 标准本身不回答，靠本地约定。约定没有版本管理，就是事故的温床。

**资源接口**：FHIR 把每个临床事实做成可寻址的资源，用 REST 读写、用订阅推送。同一条结果：

```json
{
  "resourceType": "Observation",
  "id": "obs-7781-1",
  "status": "final",
  "code": { "coding": [{ "system": "http://loinc.org", "code": "4548-4" }] },
  "subject": { "reference": "Patient/P000123" },
  "encounter": { "reference": "Encounter/V20260311-0417" },
  "effectiveDateTime": "2026-03-11T09:00:00+08:00",
  "valueQuantity": { "value": 7.8, "unit": "%" }
}
```

差别不在格式，在**可引用性**：Observation 有自己的 id，能被别的资源引用，能按患者与时间检索，能被订阅。代价是先要有稳定的患者、就诊、术语服务——这三样没有，FHIR 只能当更啰嗦的消息用。

选型的实用判据：区域内机构系统版本杂、网络不稳，用消息；院内系统较新、要做按需查询与移动端，用资源接口；两者并存是常态，中间靠集成引擎做双向转换，转换规则必须版本化。

## 三、电子病历：法律效力来自可归因，不来自扫描件

电子病历常被误解为「把纸质病历电子化」。真正的分界是三条属性：**可归因**（每条记录能定位到具体的人、时间、终端）、**不可否认**（签名后不可篡改，修改留痕且留修改理由）、**可回溯**（能看到任一时刻的病历状态）。

按这三条检查，很多「已上线电子病历」的机构其实只做到了第一条的一半：登录用科室公用账号，签名是批量代签，修改不留痕，归档后仍可编辑。这样的系统在纠纷中提供的证据力，不如一份有医师手写签名的纸。

结构上有两种主流模型。**文档模型**（如 CDA）把一次就诊组织成一份有章节的文档，适合交换与归档，阅读体验接近纸质病历。**资源模型**（如 FHIR）把血压、用药、诊断拆成独立资源，适合计算与复用，但「一次性看完整本病历」需要额外拼装。成熟做法是两者并用：资源用于业务与科研，文档用于归档与交换，文档由资源快照生成，生成时刻与哈希一并留存。

「叙构结合」是中文病历的折中：主体保留自然语言叙述（医案的推理过程本身有信息价值，压成字段就没了），关键要素抽成结构化字段（主诉、现病史要点、舌脉、诊断、方药）。抽取边界要提前定，且要接受一个事实——抽得越多，医师越不愿写；抽得越少，数据越不可算。可行的比例通常是：诊断、手术、用药、关键检验必结构化，叙述性内容只做关键词标注，不强制成字段。

智能病历的应用要守一条线：**生成可以，签名必须是人**。模型起草的病程记录，医师逐句确认后才能签名；系统日志要区分「起草」与「确认」两个动作。把两者合并成一个按钮，等于把责任转移给了模型，而模型不承担任何责任。

## 四、患者主索引：脏数据的总源头

所有跨系统的分析，最后都会落到「这是同一个病人吗」。患者主索引（MPI）做不好，后面的合并、随访、费用分析全部带偏，而且错误会随着数据量放大。

匹配有两条路线。**确定性匹配**：身份证号或医保号完全一致才合并，准确率高、召回低，遇到无证患儿、外籍患者、急救无名氏就断链。**概率匹配**：按姓名、性别、出生日期、地址、电话加权打分，超过阈值自动合并，介于两阈值之间转人工。概率匹配的难点不在算法，在阈值——阈值低了把两个人并成一个（病历串号，后果严重），高了同一人多个号（统计重复，后果较轻）。所以工程上普遍采取**宁可漏并、不可错并**的偏置。

一个可用的评分骨架（示意，权重须按本地数据标定）：

```js
const W = { name: 0.35, birth: 0.30, sex: 0.10, idLast4: 0.15, phone: 0.10 };

function score(a, b) {
  let s = 0;
  if (a.name === b.name) s += W.name;
  else if (editDistance(a.name, b.name) <= 1) s += W.name * 0.6; // 形近字、少一笔
  if (a.birth === b.birth) s += W.birth;
  else if (sameYearMonth(a.birth, b.birth)) s += W.birth * 0.5;
  if (a.sex === b.sex) s += W.sex;
  if (a.idLast4 && a.idLast4 === b.idLast4) s += W.idLast4;
  if (a.phone && a.phone === b.phone) s += W.phone;
  return s; // ≥0.90 自动合并；0.75–0.90 人工复核
}
```

两个必须配套的机制。其一，**合并可逆**：合并要留操作日志与原号映射，允许拆分，否则一次错并无法挽回。其二，**不覆盖原始值**：合并后保留各来源的原始姓名与证件号，展示层选一个「主记录」，而不是把其余值删掉。

主数据不止患者。科室、人员、收费项目、药品、诊断、手术六类字典同样要管，核心是**变更带生效时间**：一个科室改名，历史数据仍应显示当时的名称，否则三年前的报表会随着今天的改名而变形。这是双时态建模要解决的问题——记录「事实发生的时间」与「系统记录的时间」两个维度，缺一个就无法回答「当时是怎么记的」。

## 五、利用边界：二次利用是另一条合规链

临床数据用于诊疗，与用于科研、管理、对外合作，是两条不同的合规链。前者在诊疗目的内，后者属于二次利用，需要重新评估目的、范围与风险。

三条可操作的边界：**去标识后再出域**（姓名、证件号、住址、联系方式、精确日期一律处理）、**最小数据集**（能给药学部的，不必给全院；能给聚合结果的，不必给行级数据）、**用途登记**（谁、为什么、取了哪些字段、保留了多久，要有台账）。第三条最容易被当成形式，但它是事后唯一能界定范围的东西。

对外合作还要加一条：**衍生数据的归属与退出**。模型在本地数据上训练出的参数、特征、标注，算谁的；合作终止后对方是否删除原始数据与衍生数据。这些不写进协议，技术上无法补救。

## 六、代价与边界

- 本章的检验条数、缺失比例均为**演算设定**，用于说明三方对账的方法，不代表任何机构的实测结果。
- 消息与资源示例为结构示意，字段取值经过简化；落地须按所选标准版本与本机构的值域改造。
- 强调「单一权威来源」不等于「只用一个系统」。多系统是现实，关键是副本可校验、冲突有裁决规则。
- 主索引的概率匹配涉及个人信息处理，合并与拆分都要留痕并接受审计；阈值不得为了「看起来干净」而调低。
