# 第 5 章 · 技术与资源检索：检索能力决定你能看见多少证据

> **MOTTO:** 「君子生非异也，善假于物也。」——《荀子·劝学》
>
> **PROBLEM:** 一位临床药师被问到「某含丹参的中成药与华法林同用有无风险」。她在院内知识库检索「丹参 华法林」，命中 0 条；在中文文献库检索同一组词，命中 214 条，但前 20 条里 13 条是综述、6 条是动物实验；在外文库用「Salvia miltiorrhiza warfarin」检索，命中 8 条，其中 2 条是病例报告。三小时过去，她拿到的是一堆标题，不是一个能回答问题的证据集。问题不在她不会查，而在她没有被教过「检索是一件可以被评估的事」。

**双根因定位:** 环境逼迫（临床问题按分钟计，检索结果按年增长，任何一次检索都不可能「查完」）+ 知识积累（信息检索课长期教工具操作、不教评估方法：没有金标准集，就无法知道自己的检索漏了多少、多了多少）。

## 一、检索式的四个变量

任何一次可复现的检索，都由四个变量决定。把这四项写下来，别人才能重跑你的检索；缺一项，结果就不可复核。

| 变量 | 内容 | 常见错误 |
|---|---|---|
| 词 | 主题词与自由词，含同义词、旧称、拉丁名、商品名 | 只用一个俗称 |
| 字段 | 题名、摘要、主题词、全文 | 全用全文，噪音淹没结果 |
| 逻辑 | AND / OR / NOT 与括号 | NOT 用得太早，砍掉相关文献 |
| 限定 | 年限、语种、研究类型、人群 | 年限随意设，漏掉经典研究 |

把临床问题转成检索式，常用 PICO 框架：人群（P）、干预（I）、对照（C）、结局（O）。上面那个问题拆开是：服用华法林的患者（P）、联用含丹参制剂（I）、未联用（C）、出血事件或 INR 波动（O）。拆完就会发现，原检索式缺了 O，也缺了「INR」这个关键自由词——这正是命中率低的直接原因。

中医与中药检索还有两个特有难点。其一是**异名同物**：同一味药有正名、别名、地方名、炮制品名、拉丁学名，只查一个名字必然漏。其二是**同名异物**：不同基原共用一名（历史上木通一药即有关木通、川木通之别），只按名称检索会把安全性完全不同的研究混在一起。可行的做法是建一份本地同义词表，检索时自动展开，并把基原作为独立限定条件。

## 二、查全与查准：两个可以算的数

检索质量不是感觉，是两个比率：

- **查全率（召回）** = 检出的相关文献 / 全部相关文献
- **查准率（精确）** = 检出的相关文献 / 检出的全部文献

分母「全部相关文献」在真实世界里未知，所以工程上用**金标准集**近似：请专家就同一问题手工确认 30–50 篇必读文献，构成 gold set，然后看你的检索式命中了多少。这个方法便宜、可重复，比争论「感觉查得挺全」有用得多。

举个可以手算的例子（演算设定）：金标准集 40 篇，检索式 A 命中 52 篇，其中 26 篇属于金标准集，则查全率 65%、查准率 50%。若把「丹参」扩展为「丹参 OR 赤参 OR Salvia miltiorrhiza」，命中升到 96 篇，金标准集覆盖 36 篇，则查全率 90%、查准率 37.5%。这就是典型的取舍：**扩展同义词提高查全、牺牲查准**。做系统评价要偏查全，做快速问答要偏查准，两者不应用同一套检索式。

```js
// 用 gold set 评估检索式：输入命中集合与金标准集合
const recall = (hits, gold) => gold.filter((d) => hits.includes(d)).length / gold.length;
const precision = (hits, gold) => hits.filter((d) => gold.includes(d)).length / hits.length;
```

还有一个常被忽略的指标：**可复现性**。同一检索式隔三个月重跑，结果集应当只增不减（新文献入库），不应无理由减少。若减少，说明数据库订阅、索引或限定条件发生了变化——这在写系统评价的方法学部分时必须交代。

可复现的前提是**检索过程留档**：数据库与版本、检索日期、完整检索式、限定条件、命中数、去重后条数、纳入排除的每一步数量。这份记录的价值在半年后显现——当结论被质疑时，能拿出当时到底查了什么。很多机构的「证据检索」无法复核，不是方法错，是只留了结果、没留过程。

检索还有一个组织层面的问题：谁负责维护检索能力。把检索完全交给个人经验，人员一变动，能力就归零。可行的安排是设一个兼职的「信息专员」角色，负责维护同义词表、金标准集、常用检索式的模板库，并每季度更新一次。这个角色不需要是图书馆学专业出身，需要的是愿意把经验写成可复用的规则。

## 三、院内资源：先组织，再检索

医院里的知识资源通常有五类：诊疗指南与专家共识、临床路径、处方集与药品说明书、检验手册与参考区间、病历与医案。它们的共同问题不是缺，而是**散且版本不明**。

组织的最低要求是三件事：**统一入口**（一个检索框能覆盖多源，而不是让用户记住五个系统）、**元数据**（标题、发布机构、版本、生效日期、适用人群）、**版本可见**（检索结果里直接显示「2023 版，已被 2025 版替代」）。第三件最重要：临床最怕的不是查不到，是查到一份已经废止的推荐。

知识组织还有一层结构工作——把「概念」从「文献」里拆出来。指南里的一条推荐、说明书里的一条禁忌、路径里的一个节点，都是可独立引用、可独立更新的知识单元。拆出来的好处是能精确回答「这条建议出自哪里、什么时候生效」；不拆的后果是所有更新都只能整篇替换，实际结果是没人更新。

中医文献资源还有其特殊性：古籍的版本差异、异体字、通假字、无名方，使全文检索的召回天然偏低。可行的补救是双轨——原文库保留影印与校勘本，检索层加异体字归一与方名别名表；不要指望一个通用分词器能处理「㵴」「鞕」这类字。

## 四、技术选型：先划责任边界，再谈先进

云与大数据的选型，管理上先要回答一个问题：**哪些责任随服务一起转移，哪些永远在自己身上**。

| 模式 | 厂商管 | 自己管 | 医疗场景的常见误判 |
|---|---|---|---|
| IaaS | 机房、硬件、虚拟化 | 系统、补丁、数据、备份 | 以为买了云就不用运维 |
| PaaS | 运行时、中间件 | 应用、配置、数据 | 以为数据自动合规 |
| SaaS | 应用与升级 | 账号、权限、数据内容、导出 | 以为厂商负责隐私 |

无论哪种模式，**数据分级、访问授权、导出管控、审计留痕**四项永远在机构自己身上。SaaS 病历系统最容易出的问题不是宕机，而是「谁能导出」没约定：厂商运维人员为了排障要库权限，医院为了省事给了常设账号，导出行为无人审。合同里要写清：运维访问须审批、须留痕、须最小化，且不得将数据带出约定地域。

技术选型还有四个管理判据，比参数表有用：**总拥有成本**（含接口改造、培训、运维人力，通常许可费只占三成）、**退出成本**（数据能否完整导出、格式是否开放、迁移要多久）、**接口开放度**（是否有文档、是否限流、是否收费）、**厂商存续风险**（小厂商的产品在三年后是否还有人维护）。

## 五、大数据与 AI：能力边界写在数据里

医院说「上大数据」，实际要解决的通常是三类问题：多源数据的整合查询、时序指标的监测、以及基于历史数据的预测。三类的技术路径不同，混在一个平台里往往哪类都做不好。

批处理适合日结报表与历史分析，流处理适合危急值、院感预警这类分钟级场景。选错模式的表现很典型：用批处理做实时预警，延迟两小时，临床不用；用流处理做年度报表，资源浪费且难维护。

AI 在医学信息场景里目前较稳的用法是**辅助检索与辅助书写**，较不稳的是**直接给结论**。以检索增强为例：模型基于院内指南回答问题，并给出引用段落——这比纯生成可靠，但仍需两步核验：引用是否真实存在、引用是否支持结论。工程上要强制显示原文片段与出处，不允许只给一段流畅的话。没有出处的答案，在医疗场景里不是答案，是风险。

模型评价也有边界。AUC 0.85 说明在特定人群、特定时间窗内的区分度，不说明在另一家医院同样有效；阳性预测值随患病率变化，把一个筛查模型搬到患病率低十倍的场景，假阳性会成倍上升。所以模型上线前必须做本地验证，上线后必须持续监测漂移。
本章可直接验证：`node code/main.js` 打印结构清点与判据清单（数字从 `docs/zh.md` 现算），`node --test code/main.test.js` 跑本章单测；两条命令只读正文与代码，不写任何文件。

## 六、代价与边界

- 本章的命中数、查全率与查准率均为**演算设定**，用于演示评估方法，不对应任何真实检索结果。
- 同义词表、金标准集都需要持续维护，这是一项长期人力投入，不是一次性配置。
- 云服务的责任划分以合同为准，本章表格是通用示意；签约前须由法务、信息、临床三方共同确认数据条款。
- 检索与 AI 辅助都不能替代临床判断。任何用于诊疗决策的输出，必须可追溯到原始证据，并由有资质的人员确认。
