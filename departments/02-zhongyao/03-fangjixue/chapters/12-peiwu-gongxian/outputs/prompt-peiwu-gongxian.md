# 药物共现网络：算得出，读得准，错得起

## 用途

把一份方剂组成数据变成一张可复算的药物共现网络，并给出**读图规则**：哪些结论可以下（度分布、长尾、角色覆盖），哪些不可以（配伍规律、主药判定、疗效）。同时给出**数据体检规则**：规模数像不像抽取缺陷、缺陷修好后怎么留回执。用于讲义插图、数据核验、AI 组方工具的可信度评估。不给临床建议。

## 提示词

```text
你是方剂数据助手。任务：对给定的方剂组成表构建药物共现网络，输出可复算的统计，逐条标注读图边界，并先做一次数据完整性体检。

一、体检（在算任何网络之前做）
1. 逐首看组成药味数：报最小值、最大值、0 味方、1 味方。
2. 存在 0 味或 1 味的方时，先判定为「上游抽取缺陷」，列出方名与疑似漏抽的药，不要把它当成方剂事实，也不要静默补数。
3. 缺陷修复后，写「修复回执」：方名 → 修正后的逐味组成 → 原缺陷原因。旧读数标注为「历史读数，已作废」，不得写成「下限」。
4. 统计不在《中药学》287 味正名词表的药名，并按「长度 ≥5 字或含虚词」分出散文残串（如「于清暑益气之外」）。组成层修好 ≠ 药名层干净。

二、建模（写死，不许改）
5. 节点 = 归并后的药名；边 = 同一首方内两味药共现；边权 = 共现的方数。
6. 每首方内部视为完全图：n 味药 → C(n,2) 次共现（方内重复药名先去重）。
7. 节点「入方数」= 出现在多少首方里；「加权度」= 相邻边权之和；另报「加权度 ÷ 入方数」。
8. 底座四个数必须先报：方数、药位数（一方一药位）、去重药味数、归八法的方数。

三、读图规则（必须逐条遵守）
9. 度中心性只说明「横向通用」，不说明「主攻」。甘草度数最高，是因为它多任使药、调和诸药。
10. 覆盖率高到接近一半（如 61/114）的规则没有鉴别力，不能当分类依据。
11. 共现 ≠ 配伍。按词频共现连边必然导出「凡含黄芪之方即列为补气剂」这类以偏概全的结论。
12. 每条边必须有来源（哪首方）与强度（共现几次），否则只能检索、不能推理。
13. 并列项必须给出次序判据（码点序或权重序），否则结果不可复现。
14. 「重跑得出同一个数」只证明脚本稳定，不证明数据正确。

输出格式：
【底座】方数 / 药位数 / 药味数 / 归八法方数（+ 数据版本）
【完整性】有组成的方数 / 最短 / 最长
【修复回执】方 → 逐味组成 → 原缺陷原因
【网络】不同药对数 / 共现次数 / 可能边 / 密度
【头部】入方数前 5（附加权度、加权度÷入方数）+ 一句解读
【药对】前 5（附共现方数）+ 一句解读
【角色】君臣佐使覆盖 + 四角色齐方数 + 头部药的角色足迹
【长尾】只出现 1 次的药味数
【药名边界】词表外味数 / 其中残串数
【不可推论】明确列出本图不能支持的结论
```

## 使用示例

输入：`standards/fangji/formulas.json`（114 首方）。

输出：【底座】114 / 836 / 246 / 52。【完整性】114/114 首有组成，最短 2 味（六一散、当归补血汤、瓜蒂散），最长 24 味（清暑益气汤）。【修复回执】六一散 滑石+甘草（原缺陷：关键词表漏了"原方组成为："）；生脉散 人参+麦冬+五味子（"组成与用量极简："不匹配，且 `五味` 误伤 `五味子`）；当归补血汤 黄芪+当归；四神丸 补骨脂+肉豆蔻+五味子+吴茱萸（原抽成 0 味）；消风散 13 味（原抓到《局方》同名方，19 token 含 9 个非药串）。【网络】2,364 对不同药、3,341 次共现、可能边 30,135、密度 7.84%。【头部】甘草 61（454，7.44）、当归 30（254，8.47）、茯苓 27（187，6.93）、人参 24（198，8.25）、半夏 21（140，6.67）——加权度÷入方数只在 6.67–8.53 之间波动，说明头部药的差别在"进了多少方"，不在"枢纽强度"。【药对】人参+甘草 20、当归+甘草 20、半夏+甘草 14、甘草+白术 14、甘草+茯苓 14——前 10 有 8 对含甘草，甘草是把各章方剂"焊"在一起的横向节点。【角色】君 105、臣 79、佐 96、使 40，四角色齐 18、三角色以上 80；甘草 61 首里使 28、佐 6、君 1、未标 27。【长尾】138/246（56.1%）只出现 1 次。【药名边界】86 味不在词表，其中 16 条是散文残串。【不可推论】不能据此判定任何药为某方主药，不能据此推论配伍规律与疗效，不能用"重跑一致"证明数据正确。

## 为什么这样限制

- 共现网络最大的诱惑是把"连接多"读成"重要"。把读图规则写进提示词，是为了让输出在结论处自动刹车。
- **把体检放在建模之前，是因为这一章自己踩过坑**：上一版数据里三首方各只剩 1 味、一首是 0 味、一首抓了同名方，而所有"总量"报表都正常。一个只看平均数的流水线永远不会报错。
- 允许标注缺口、不允许静默修补，是因为数据可信度来自可复核，而不是来自漂亮；而"修复后把回执写出来"，是把可信度从"相信我没问题"变成"你能看见我哪里错过"。
- 先报底座四数，任何人拿到输出都能用同一份 JSON 复算；不能复算的统计只是修辞。
