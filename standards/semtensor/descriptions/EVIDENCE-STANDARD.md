# 外部证据判定标准（external.json）

> 这份文件定死一件事：**「取到证据」是什么意思**。
> 96 个证名按 ICD-11 标准命名，其中 20 余条是「A、B证(病名)」这种一个名称带多个构件的形态。
> 这类合称在中文临床文献里几乎不会逐字出现，于是「算不算取到」会出现两套尺度 ——
> 不同的人跑同一批，覆盖数不一样，数字就不可比。
> 判定由 `scripts/lib_evidence_scope.js` 执行，`--audit` 与 `build_dsu_descriptions.js` 都调它，
> **不允许在别处另写一套判断。**

## 1. 三条口径

1. **证据边界 = 入库的 `title` + `snippet`。**
   `snippet` 入库时截到 600 字。超出这个边界的内容一律不算证据 ——
   证据必须能被后来的人就地复核，页面上别处的文字不是"已取回的证据"。

2. **括注不参与构件判定。**
   `气滞血瘀证(颈部)` 的「颈部」是病名/部位限定，它决定"证据是否对题"，
   不决定"构件是否齐"。构件按名称本体里的 `、` 与 `/` 切分（`阳明腑实证/结胸证` 是两个构件）。

3. **两级分开报数，不合并。**
   整串级和构件级不是同一强度的证据。把两者并成一个「75/96」，
   会让弱证据看起来和强证据一样硬。

## 2. 四种判定

| scope | 含义 | 强度 | 计入哪个数 |
|---|---|---|---|
| `single` | 证名只有一个构件，且有来源覆盖它 | 强 | 整串覆盖 |
| `whole` | **某一条**来源的 title+snippet 同时覆盖全部构件 | 强 | 整串覆盖 |
| `component` | 各构件分别被覆盖，但没有一条来源同时覆盖全部 | 弱 | 构件覆盖（单列） |
| `partial` | 有构件完全没被覆盖 | **不合格** | 不计入，需重查 |

两条容差，除此之外不做任何同义改写：

- **「证」是类别后缀**：`脾胃湿热证` 允许由「脾胃湿热」命中。
- **繁简归一**：`肝陽上亢證` 判为「肝阳上亢证」。只用于判定，不改写入库文本；
  表在 `lib_evidence_scope.js` 的 `SIMP`，只收证名/症状词里会出现的字。

同义关系（`肺阴亏虚` = `肺阴虚`）**不在这条规则里处理**，它在 `aliases.json`。
判定只回答"存证文本里有没有这个名字"，不回答"这是不是同一个证"。

### 并病（两证同存）另用一条判据

`肝火亢盛、气阴两虚证（瘿病）`、`胆郁痰扰、心神不宁证(惊悸/不寐)` 这类**并病**，
是两个证候**同时存在**，不是一个文献里有固定写法的"复合证"。对它们：

- **名称不拆**：仍是一条 DSU、一个 label，不拆成两条证名（用户 2026-10-18 明示）；
- **判据换成"两侧各有来源"**：`scope=component` 即为达标，**不要求某一条文献写出整串**；
- 哪些是并病是**领域判断**，不是脚本猜的。标记写在 `external.json` 的 `concurrent` 字段
  （`scripts/mark_concurrent.js` 写入，可 `--off` 撤销），并记 `concurrentWhy` 说明依据；
- 统计上单列「**并病达标**」，与非并病的「构件级（弱）」分开报 —— 两者证据强度不同，
  合并会把弱证据洗白。

判定链：`lib_evidence_scope.js` 出 `scope` → `external.json` 的 `concurrent` 是领域标注 →
`build_dsu_descriptions.js` 据此分四级报数 → 平台层读 `externalScope` + `externalConcurrent`（因果链另见下节）。

### 因果链（一证为因、一证为果）是第四类

有些名字里的「、」既不是并病，也不是两个并列构件，而是**一条病机的先后**：
`热毒犯肺、痰瘀阻络证(哮喘性支气管肺炎)` —— 热毒犯肺是始动病机，痰瘀阻络是它的后果
（热毒灼津 → 痰阻肺络 → 久则血瘀）。对这类：

- **名称同样不拆**（一条 DSU、一个 label）；
- **判据与并病同级**：同一病种（中医病名层，如「肺炎喘嗽」范畴）内，**因、果各有一源** 即达标；
- 标记写在 `external.json` 的 `relationChain: "cause-effect"` 字段（另 `relationWhy` 记依据；
  `scripts/mark_relation_chain.js` 写入，可 `--off` 撤销。与 `concurrent` 互斥 —— 脚本拒绝同挂，
  `tests/test_external_batch.js` 也钉住）；
- 报数**单列「因果链达标」**，既不与整串级合并，也不与并病混计 —— 两者证据强度相同，语义不同
  （因果链是先后，并病是同存）；
- 与并病**互斥**：同一条目不可能既标 `concurrent` 又标 `relationChain`（测试里已钉住）。

`scripts/lib_evidence_scope.js` 不需要认识它：分类仍由文本覆盖得出 `component`，
"达标"是构建层按领域标注算的 —— 与并病的处理方式一致，避免出现第二套判定。

判定链（含因果链）：`classify()` 出 `scope` → `external.json` 的 `concurrent` / `relationChain`
是领域标注 → 构建分四级报数 → 平台层读 `externalScope` + `externalConcurrent` + `externalChain`。

### 枚举页不算整串级（2026-10-22 补）

按 `classify()` 的文本覆盖，一个把几个证型**并列列出**的页面（诊疗方案的「辨证分型」表、
肥胖分型科普、硬皮病证型枚举）也会被判成 `whole` —— 因为它同时出现了两个构件的字面。
这类页面**没有断言这两个构件属于同一个证**，拿它升整串级等于用列表页刷指标：

- 例：`痰湿内盛、脾虚不运证` ← 深圳市卫健委《中医对肥胖的认识及分型》把两者列为肥胖的两个**不同**证型；
- 例：`气阴两虚、痰瘀阻络证` ← 消渴病痹症诊疗方案把两者列为并列证型；
- 例：`肝阳上亢、风阳上扰证` ← 百度健康条目在讲**如何区分**二者。

判据：来源必须是**一句断言**（同一患者的病机、因果、或"X 与 Y 并见"），
不是「A 是一型 / B 是一型」的并列。**宁留构件级，不刷整串级** —— 构件级是合法结果，不是待修的残缺。
本条只写人工判断，不进 `classify()`：文本覆盖能判"字在不在"，判不了"是不是同一件事"。

## 3. 为什么写这份标准（两次实跑教训）

- 第一版口径要求逐字带「证」，**57 条被误判不合格** —— 它们的来源写的是「脾胃湿热」「湿热下注」。
  误判方向是**假阴性**：好证据被记为不合格，比假阳性更难发现（它不报错，只是数字变低）。
- 第二版对繁体来源仍然误判一条（`肝陽上亢證`）。繁体来源在这个语料里不是边角：
  香港中文大学、台湾卫福部、韩药资源研究中心都是可达且有价值的来源。

## 4. 操作流程

```bash
node scripts/external_batch.js --status          # 还差多少 + 当前租约
node scripts/external_batch.js --next -n 6       # 取一批（含「、」的会给 parts；先看退出码）
# …检索、按「只记真正取回的来源」整理…
node scripts/external_batch.js --import batch.json   # 入库即定级（scope 自动写）并释放租约
node scripts/external_batch.js --audit               # 口径变动或手改后重算全库
node scripts/build_dsu_descriptions.js               # 出 descriptions.md（两级分开计）
```

### 并发闸门（租约）

同一个 job 会被并发跑：2026-10-18 实测 05:48 / 08:03 / 12:42 / 16:02 四条批次提交，
其中两条不在调度时间点上（同日多会话各取了一批），两次运行的检索因此完全重复。

- `--next` **取批即写租约**（`.cache/external_batch.lease.json`，已 gitignore），TTL 120 分钟。
- 第二个运行的 `--next` 直接**退出码 3** 并打印持租者；**它必须就此收工**，不检索、不 import、不提交。
- `--import` 写完释放；`--release` 手工释放；`--next --force` 强行接管；`--renew` 续租。
- 租约**不绑 PID**：`--next` 一返回进程就退出，而"取批→检索→入库"是跨进程的一段时间，
  按 PID 存活判断会让第二个运行永远接管 —— 第一版就是这么失效的（TTL 才是唯一可靠的判据）。
- 租约只管"别重复取同一批"；写冲突另有 `--import` 的读入指纹校验兜底。

#### TTL 为什么是 120 分钟（不是拍脑袋）

实测 `cron/executions.db` 里本 job 的 **11 次执行**（2026-10-15 ~ 10-18）：

| 统计 | min | p50 | p90 | max |
|---|---|---|---|---|
| 成功批次（n=10） | 1.5 | 2.5 | 4.1 | **5.7 分钟** |
| 含 1 次 failed | 1.5 | 2.7 | 5.7 | **59.2 分钟** |

那次 59.2 分钟的 failed 正是**调度器 ~60 分钟兜底杀进程**的时间点。
所以 TTL 不能按"平时 2.5 分钟"来定 —— 第一版设 45 分钟，比这个硬上限还短，
一个活着的长跑会在第 45 分钟被判过期、被抢走。现在取 120 分钟 = 硬上限的 2 倍：
活跃运行不会被抢，真挂死的运行最多占 2 小时，而调度间隔 8 小时，不挡下一个计划批次。
超过 2 小时的交互式会话用 `--renew` 续租。

- **入库即定级**：`--import` 会给每条写上 `scope`。
- **`partial` 不删**：它的来源有溯源价值（往往描述症状而不写证名）。
  重查时先 `--requery "<证名>"` 退回队列，按新口径重新取。
- **`--audit` 会打印改判清单**，口径改动的影响面必须看得见。
