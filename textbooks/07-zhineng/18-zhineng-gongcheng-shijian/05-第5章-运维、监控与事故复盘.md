## H.1 本章要解决的问题

系统上线后，事故不是「会不会发生」而是「什么时候发生」。区别在于：有监控的团队在用户投诉前发现，没监控的团队在领导问起时才知道。事故复盘的目的不是追责，而是把「这次靠人扛过去」变成「下次系统自己扛」。

## H.2 本章目标（可检验）

- 建立最小可用监控面板（可用性、时延、错误率、业务量、模型漂移）
- 完成一次事故复盘：时间线、根因、影响面、改进项与责任人
- 把至少一项人工处置转化为自动化（告警+脚本或校验）

## H.3 操作流程

1. 资产清单：服务、依赖、数据源、模型版本、证书与密钥到期时间；每项有责任人
2. 监控面板：四个黄金指标（延迟、流量、错误、饱和度）+ 业务指标（调用量、采纳率）+ 模型指标（输入分布偏移、置信度分布）
3. 日志与追踪：统一请求 ID，贯穿调用链；日志保留期与检索方式写明
4. 告警分级：P1（服务不可用/数据泄露）、P2（功能受损）、P3（体验下降）；每级响应时限与通知渠道不同
5. 值班与升级：谁看告警、多久响应、多久升级、升级给谁
6. 备份与恢复：数据备份频率、恢复演练记录、RTO/RPO 目标
7. 事故处置：先止血（回滚/降级/限流）再定位；处置过程按时间点记录
8. 复盘会：48 小时内开，参与人含研发、运维、业务；只谈事实与机制，不评价个人
9. 根因分析：用 5Why 追到机制层，区分「直接原因」与「系统性原因」
10. 改进项：每条含动作、责任人、截止时间、验证方式；区分「立即」「季度」
11. 自动化转化：至少把一项人工处置做成脚本或校验（如自动重启、自动回滚、异常输入拦截）
12. 复盘报告：按 H.5 模板成文并归档，改进项进入跟踪表

## H.5 模板：事故复盘报告与改进跟踪表

| 字段 | 填写要求 |
|------|----------|
| 事故概要 | 时间、影响面、持续时间、分级 |
| 时间线 | 发现—确认—止血—恢复—复盘各时间点 |
| 直接原因 | 触发事件与失效点 |
| 系统原因 | 5Why 追到的机制问题 |
| 影响评估 | 用户数、数据安全、业务损失 |
| 处置过程 | 止血措施、回滚/降级、效果 |
| 改进项 | 动作、责任人、截止、验证方式 |
| 自动化 | 人工处置转自动化的实现 |
| 监控缺口 | 本次为何未提前发现，补充了什么 |
| 附件 | 日志片段、告警记录、时间线截图 |

> 本表是本章的交付物：事故后 48 小时内成文；改进项按周更新跟踪表，直至验证关闭。

## H.6 常见失效与处置

- **复盘变成追责会** → 下次没人敢报事故；事实会被隐藏
- **只写直接原因** → 不追机制，同类事故必然重演
- **改进项无责任人** → 清单写完就搁置
- **监控只看技术指标** → 模型漂移与业务异常无人发现
- **不演练恢复** → 备份「有」但恢复不了，等于没有备份
- **人工处置不自动化** → 同一个问题每次都要人半夜起来处理

## H.7 出科考核

- 监控与告警覆盖（25%）
- 复盘质量与根因深度（35%）
- 改进项可验证性（25%）
- 自动化转化（15%）
