## H.1 本章要解决的问题

从「评测集 92%」到「病房里用起来」，中间隔着一整套工程问题：接口延迟、系统兼容、医生不信任、出错了没人知道。灰度验证的意义是把风险限制在小范围、可回滚、可观测——先让 5% 的调用走新版本，看真实世界指标，再决定是否放量。

## H.2 本章目标（可检验）

- 完成一次灰度发布：分流规则、监控指标、回滚条件与操作手册
- 建立真实世界监测指标（调用量、时延、采纳率、纠错率、异常率）
- 产出灰度报告：放量/暂停/回滚的结论与依据

## H.3 操作流程

1. 部署前检查：环境一致性（依赖、模型版本、配置）、接口连通性、权限与审计开关
2. 分流设计：按用户/科室/时间段分流，比例从 5% 起；保证同一患者在同一轮次内不跨版本（避免结果矛盾）
3. 对照设计：保留对照组（旧版本或人工基线），记录两组的输入分布是否可比
4. 监控指标：技术指标（QPS、P95 时延、错误率）+ 业务指标（采纳率、修改率、驳回率）+ 安全指标（越界建议、缺失提醒）
5. 告警阈值：为每类指标设阈值与通知对象；阈值要能区分「偶发抖动」与「持续劣化」
6. 回滚条件：写明触发条件（错误率 >X%、P95 >Ys、严重不良事件 1 例）与回滚操作步骤（含预计耗时）
7. 使用培训：给一线的一页说明（能做什么、不能做什么、如何反馈问题），并请 2–3 人试讲
8. 问题反馈通道：入口在哪、多久响应、谁处理；记录每一条反馈与处置
9. 灰度周期：按调用量或时间设定（如 2 周或 500 次调用），到期评估
10. 评估：与对照比较采纳率与异常率，结合失败案例判断是否放量
11. 结论与放量：放量/暂停/回滚三选一，写明依据与下一步
12. 复盘：写清「如果只允许一个监控指标，你选哪个，为什么」

## H.4 现场清单（逐项打勾，缺一项不算完成）

- [ ] 部署前环境与依赖一致性已核
- [ ] 分流比例与规则已定，患者不跨版本
- [ ] 对照组已设，输入分布可比性已检查
- [ ] 技术/业务/安全三类指标均已埋点
- [ ] 告警阈值与通知对象已配置
- [ ] 回滚触发条件与步骤书面化，含预计耗时

## H.5 模板：灰度发布方案与报告

| 字段 | 填写要求 |
|------|----------|
| 部署检查 | 环境、依赖、模型版本、权限、审计 |
| 分流 | 规则、比例、患者一致性约束 |
| 对照 | 对照组定义、输入分布可比性 |
| 指标 | QPS/时延/错误率；采纳率/修改率；安全指标 |
| 告警 | 阈值、通知对象、抖动与劣化区分 |
| 回滚 | 触发条件、步骤、预计耗时、责任人 |
| 培训与反馈 | 一页说明、试讲记录、反馈通道与时限 |
| 周期 | 调用量或时间门槛 |
| 评估 | 与对照对比、失败案例 |
| 结论 | 放量/暂停/回滚 + 依据 + 下一步 |

## H.6 常见失效与处置

- **一次性全量上线** → 出问题影响全院，且无法归因
- **同一患者跨版本** → 同一患者两次结果矛盾，信任瞬间崩塌
- **只监控技术指标** → 时延正常但医生不用，等于没上线
- **回滚没演练** → 真出事时回不去，或回滚耗时数小时
- **无反馈通道** → 问题散落在口头抱怨里，永远修不完
- **灰度期无限延长** → 没有退出条件，项目停在「试点」
