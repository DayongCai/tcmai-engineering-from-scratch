## H.1 本章要解决的问题

医疗 AI 项目最常见的返工点在起点：模型做完了才发现数据不能出库、不能用于训练、或不能接入院内系统。合规不是最后补一份说明，而是决定「能不能做、怎么做」的前置条件。这一章要产出的是边界文件：数据从哪来、能做什么、不能做什么、谁签字。

## H.2 本章目标（可检验）

- 完成数据清单与用途映射：每个数据源对应允许用途与禁止用途
- 识别三类合规风险（来源合法性、去标识化、二次使用与对外提供）并给出处置
- 产出可签字的需求与合规边界文件，作为后续设计与验收依据

## H.3 操作流程

1. 业务问题定义：写清使用者是谁、在什么场景用、输入什么、输出什么、错了会怎样（危害分级）
2. 需求清单：功能需求 + 非功能需求（时延、并发、可用性、可解释性要求），每条给验收方式
3. 数据清单：逐个数据源列「系统名—字段—更新频率—责任人—授权依据」，缺授权依据的标红
4. 用途映射：每个数据源 × 每个用途（训练/评测/展示/对外）打勾或叉，叉要写原因
5. 去标识化方案：直接标识（姓名、身份证、电话、住址）、准标识（生日、就诊日期、邮编）、敏感属性（诊断、影像）；说明处理方式与残留风险
6. 合规审查点：知情同意范围、伦理审批（如涉及研究）、数据出境、第三方模型服务（是否把数据发到外部 API）
7. 安全等级：按院内数据分级给出存储、传输、访问控制要求（加密、审计日志、最小权限）
8. 危害与兜底：输出错误的后果分级（建议性/辅助决策/直接影响处置），每级对应的提示语与人工复核要求
9. 边界文件成文：能做/不能做两张清单，逐条可核对
10. 评审：由业务、信息、合规三方会签；未签字的项不得进入开发
11. 变更机制：数据源或用途变化时的重新评估流程与责任人
12. 复盘：挑一个「合规倒逼设计改变」的例子，说明早做评估省下了什么

## H.4 现场清单（逐项打勾，缺一项不算完成）

- [ ] 用途映射逐源逐用途打勾，禁止项写原因

## H.5 模板：需求与数据合规边界文件

| 字段 | 填写要求 |
|------|----------|
| 场景与使用者 | 谁用、何时用、输入输出、错误后果分级 |
| 功能需求 | 条目、验收方式 |
| 非功能需求 | 时延/并发/可用性/可解释性 + 验收方式 |
| 数据清单 | 系统、字段、频率、责任人、授权依据 |
| 用途映射 | 训练/评测/展示/对外，允许或禁止 + 原因 |
| 去标识化 | 直接/准/敏感标识处理方式与残留风险 |
| 合规审查 | 知情同意、伦理、出境、外部 API |
| 安全等级 | 存储、传输、访问控制、审计 |
| 边界清单 | 能做 / 不能做 |
| 会签与变更 | 业务/信息/合规签字、版本、变更重评机制 |

> 本表是本章的交付物：立项时成文并会签；开发与验收阶段逐条对照，变更时更新版本号。

## H.6 常见失效与处置

- **先做模型后补合规** → 数据不可用会推翻整个技术路线，返工代价最高
- **只写「数据已脱敏」** → 未区分三类标识，残留风险无法评估
- **忽略外部 API** → 把患者数据发到第三方模型服务，是常见违规点
- **不定义错误后果** → 无法确定提示语强度与人工复核要求
- **边界文件无签字** → 无人负责的边界等于没有边界
- **不做变更评估** → 新增数据源绕过审查，事后追溯困难

## H.7 出科考核

- 数据清单与用途映射（30%）
- 去标识化与合规审查（30%）
- 危害分级与边界清单（25%）
- 会签与变更机制（15%）
